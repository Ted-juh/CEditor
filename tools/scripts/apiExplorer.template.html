Panel scripting

Adding your own behaviour to a panel

A panel can carry scripts, so it can do things the controls alone cannot: send a particular message when a button is pressed, work out one value from another, fill the whole panel from what the synth reports. You can write them in Lua, JavaScript, TypeScript, Python or a C‑like language, and they all use the same set of commands. A script behaves the same way while you are building the panel as it does in the finished plugin — if it works while you are testing it, it works when you share it.

Ten things, in the order you need them

01 · What a script is

You write the reactions; the panel decides when they run

A script is a list of things to do when something happens. You do not start it yourself and you do not tell it when to stop. Instead you write a section with a particular name, and the panel runs that section at the moment the name describes. Attach a script to a knob and give it a section called onValueChanged, and that section runs every time somebody finishes turning the knob.

Everything you can do is a command you simply call by name. Three of them — set, get and log — are always available. The rest are grouped into modules you switch on for the panel, which Modules explains. Commands in a module can be written either way: ce.midi.sendCC says which group it came from, and plain sendCC is shorter. They do exactly the same thing, so use whichever reads better to you.

There is nothing to set up first — no list of files to include, no step to run before your script works. Tick the modules the panel should have, and every command in them is ready by the time your first line runs.

A knob that sends a CC

function onValueChanged(value)
  sendCC(1, 74, value)
  log("cutoff", value)
end
function onValueChanged(value) {
  sendCC(1, 74, value);
  log("cutoff", value);
}

02 · Addressing

Every control is reached by the name you gave it

To read or change a control, you name it. Not an internal number you never see — the name in the editor. If you called a knob "cutoff", then that is what your script says. Add a dot and you can reach further in: what it is set to, what colour it is, any setting it has.

The name on its own means the control's value, so get("cutoff") and get("cutoff.value") ask the same question. If you later rename the control, every script that mentions it is updated to match, so nothing breaks.

A value can be read in three ways. .value is the real one you would read off the front panel, like 8000 Hz. .normalizedValue is the same thing as a position between 0 and 1, which is useful when you want two controls with different ranges to move together. .midiValue is the number that actually goes to the synth.

set tells you whether it worked. If you mistype a name there is nothing to change, so check the answer when it matters — otherwise a typo just quietly does nothing.

Reading and writing

local hz = get("cutoff")
local pos = get("cutoff", "normalizedValue")

set("cutoff.value", 8000)
set("cutoff.normalizedValue", 0.5)
set("led.background.fill.colour", "#39D98A")

if not set("cutof.value", 1) then
  logError("no control called that")
end
const hz = get("cutoff");
const pos = get("cutoff", "normalizedValue");

set("cutoff.value", 8000);
set("cutoff.normalizedValue", 0.5);
set("led.background.fill.colour", "#39D98A");

if (!set("cutof.value", 1)) {
  logError("no control called that");
}

03 · Writing and the synth

Changing a control normally tells the synth too

When your script changes a control, the panel treats it as though somebody had moved it by hand: the control updates on screen and the synth is told. That is almost always what you want.

There is one case where it is not. If your script is responding to something the synth just sent, sending it straight back would start the two of them talking in circles. So a change made while you are handling an incoming message is not sent back automatically. You do not have to remember this or set anything — the panel keeps track of why the change happened.

You can override it for a group of lines when you need to. A button that resets forty controls to a starting patch should update all of them and only then tell the synth; a reply confirming a setting does need to go out even though it came from an incoming message. Wrap the lines in noTransmit or transmit and normal behaviour returns as soon as the group ends, even if something goes wrong inside it.

Scoped, not per‑line

noTransmit(function()
  set("cutoff.value", 8000)
  set("reso.value", 40)
end)

transmit(function()
  sendCC(1, 74, 64)
end)
noTransmit(() => {
  set("cutoff.value", 8000);
  set("reso.value", 40);
});

transmit(() => {
  sendCC(1, 74, 64);
});

04 · Reacting

Three ways to be told that something happened

For things that happen to the control your script is attached to, write a section with the matching name: onValueChanged when its value settles, onClick when it is clicked, onNoteIn when a note arrives. Nothing else to set up — the name is the whole connection.

To hear about something else — another control, the transport, one of the components — use on and say what you are listening to: on("cutoff", "onValueChanged", …). Listen to "*" and you hear about all of them, which is why what you are handed always says which one it came from.

Two of these look almost the same and the difference is worth knowing. onValueChange runs over and over while a knob is still being turned, which suits anything on screen that should follow along. onValueChanged — note the d — runs once, when the knob is let go, which is when you want to tell the synth.

watch is the third way. It is not tied to any event: you give it something to keep an eye on, and it runs whenever that changes. Use it for the settings no event covers, like a colour or a size.

With on, both spellings of an event work — "step" and "onStep" mean the same thing, so you do not have to remember which one this page used.

Three ways to be told

function onValueChanged(value)
  sendCC(1, 74, value)
end

on("*", "onStep", function(step)
  set(step.target .. ".led", true)
end)

watch("cutoff.background.fill.colour", function(c)
  log("colour is now", c)
end)
function onValueChanged(value) {
  sendCC(1, 74, value);
}

on("*", "onStep", (step) => {
  set(step.target + ".led", true);
});

watch("cutoff.background.fill.colour", (c) => {
  log("colour is now", c);
});

05 · Modules

Switch on the groups of commands you need

There are 555 commands in all, sorted into 41 groups called modules. A panel would be needlessly large if it carried every one, so you tick the modules your panel uses and only those are included when you share it. If you are curious what that costs, What it weighs has the real figures.

ce.core is always on, and its commands never need a prefix — that is why you write plain set and get. Everything in the other modules can be written either way, so ce.midi.sendCC and sendCC are the same command.

If you call something from a module you have not switched on, nothing happens and the console tells you which module to tick. Your script keeps running.

Some commands need the panel window to be open, and the reference marks those panel view only. Drawing, asking a question and driving the components are all in that group, for the obvious reason: with the window shut there is nothing to draw on and nobody to ask. The rest, marked cross-runtime, work either way.

Two spellings, one function

-- ce.core is global
set("cutoff.value", 8000)

-- everything else, either way
ce.midi.sendCC(1, 74, 64)
sendCC(1, 74, 64)

local n = ce.music.quantize(63, 60, "minor")
local m = quantizeNote(63, 60, "minor")
// ce.core is global
set("cutoff.value", 8000);

// everything else, either way
ce.midi.sendCC(1, 74, 64);
sendCC(1, 74, 64);

const n = ce.music.quantize(63, 60, "minor");
const m = quantizeNote(63, 60, "minor");

06 · Musical time

Working in beats and bars rather than milliseconds

ce.time knows the current tempo — from the editor while you are building, or from your music software once the panel is running in it — and converts between beats and milliseconds for you. So setting a delay to a dotted eighth note, the calculation every synth panel ends up needing, is a single line.

There are three ways to make something happen later. after does it once, a given number of milliseconds from now. startTimer repeats at a fixed rate. syncTimer repeats on a musical interval — every sixteenth note, say — and speeds up or slows down with the tempo.

onBeat and onBar are checked about thirty times a second, so they land within a frame of the beat. That is close enough to light an indicator or advance a sequencer, but it is not exact to the sample, so do not rely on it for anything that has to line up perfectly with recorded audio.

Settle, then send

sendProgramChange(1, 12)
ce.time.after(40, function()
  sendDump("patch")
end)

local ms = ce.time.beatsToMs(0.75)
set("delayTime.value", ms)

ce.time.syncTimer("step", 0.25)
function onTimer(info)
  if info.id == "step" then step() end
end
sendProgramChange(1, 12);
ce.time.after(40, () => {
  sendDump("patch");
});

const ms = ce.time.beatsToMs(0.75);
set("delayTime.value", ms);

ce.time.syncTimer("step", 0.25);
function onTimer(info) {
  if (info.id === "step") step();
}

07 · Components

Setting up a component, and hearing back from it

The bigger components — the arpeggiator, chord pad, sequencers, envelope, the displays — each have their own module of commands, and the Reference shows a picture of every one. Each command starts with the name of the control, and each one tells you whether it worked. Ask for something the component does not have and it says no rather than storing a setting that does nothing.

read asks a component what it is currently set to, using the same words you would use to set it. Where a component holds a list of things — steps, nodes, breakpoints, destinations — size tells you how many there are, fill replaces them all at once, and insert and remove change one.

Components also tell you when things happen: a step playing, a scene changing, a pad being hit, a recording finishing. Those need the panel window open, since that is where the components are actually running.

Ask, set, react

if not ce.components.arp.pattern(a, "chord") then
  logError("that pattern does not exist")
end

local now = ce.components.arp.read(a, "pattern")
local n = ce.components.turing.size(t, "step")
ce.components.turing.fill(t, "step", {0, 0.5, 1, 0.25})

on(a, "onStep", function(step)
  log("step " .. step.index .. " of " .. step.of)
end)
if (!ce.components.arp.pattern(a, "chord")) {
  logError("that pattern does not exist");
}

const now = ce.components.arp.read(a, "pattern");
const n = ce.components.turing.size(t, "step");
ce.components.turing.fill(t, "step", [0, 0.5, 1, 0.25]);

on(a, "onStep", (step) => {
  log(`step ${step.index} of ${step.of}`);
});

08 · Typography

Setting text and fonts safely

You could already change any text setting with set — set("Label.Text.Font.size", 18) has always worked. So ce.text is not about reaching further. It is about three things you cannot do by writing a setting directly.

It knows which fonts exist. fonts() lists the ones you can actually pick, and font("Inter Tight") tells you about one of them, or nothing if it is not there. Ask for a font nobody has and it says so, rather than storing the name and quietly showing you something else. Check portable before you settle on a face: a built-in font works everywhere, but one from your own library lives on this computer and is not part of the panel — so it looks right while you build and falls back to something else for whoever you send it to.

It keeps related settings in step. Boldness is stored in two places, and different parts of the app read different ones. Change only one and the editor and the finished panel disagree about how bold your text is. style() always writes both, so you cannot get into that state.

It can measure text. measure() tells you how much room a control's text takes up in its own font, using the same code that draws it, so spacing and wrapping are all accounted for. fit() then shrinks the size until the text fits the control and tells you what it settled on — useful when you want to line something else up with it.

These need the panel window open, because the font list is the editor's and measuring needs something to measure on. A command that guessed the answer would be worse than one that tells you it cannot help right now.

Check, style, fit

local face = ce.text.font("Inter Tight")
if not face or not face.portable then
  face = ce.text.font("Arial")     -- survives the export
end

ce.text.style("Readout", {
  family = face.family, size = 18,
  bold = true, tabularFigures = true,
})

if face.variable then
  ce.text.axis("Readout", "wght", 620)
end

set("Readout.Text.content", patchName)
local fitted = ce.text.fit("Readout", { min = 9 })
if not fitted.fits then
  logWarn("still overflowing at " .. fitted.size)
end
let face = ce.text.font("Inter Tight");
if (!face || !face.portable) {
  face = ce.text.font("Arial");    // survives the export
}

ce.text.style("Readout", {
  family: face.family, size: 18,
  bold: true, tabularFigures: true,
});

if (face.variable) {
  ce.text.axis("Readout", "wght", 620);
}

set("Readout.Text.content", patchName);
const fitted = ce.text.fit("Readout", { min: 9 });
if (!fitted.fits) {
  logWarn(`still overflowing at ${fitted.size}`);
}

09 · Keeping things

Remembering things, for a while or for good

state is a scratch pad of your own. Anything you put in it is still there next time your script runs, and it is wiped when the panel is reloaded. It is what you want for counting things or remembering where you got to.

Settings are for things that should still be there tomorrow, and you choose how far they travel. "panel" keeps them with the panel, so they go wherever the panel goes and every script on it can see them. "script" keeps them to your script alone. "local" keeps them on this computer and out of the panel entirely — a panel you send to somebody else should not arrive carrying your choice of MIDI port.

encode and decode turn a value into text and back, which is how you fit something structured into a place that only takes text. They are here rather than borrowed from your language because not all five languages have one, and all five have to produce exactly the same text — which also means you can compare two of them by comparing the text.

Scratch, saved, shipped

state.hits = (state.hits or 0) + 1

ce.storage.saveSetting("bank", 3)
ce.storage.saveSetting("port", "IAC",
                       { scope = "local" })

local patch = { name = "Lead", cutoff = 0.75 }
sendSysex(toAscii(ce.storage.encode(patch)))

local back = ce.storage.decode(text)
if back == nil then logError("bad config") end
state.hits = (state.hits ?? 0) + 1;

ce.storage.saveSetting("bank", 3);
ce.storage.saveSetting("port", "IAC",
                       { scope: "local" });

const patch = { name: "Lead", cutoff: 0.75 };
sendSysex(toAscii(ce.storage.encode(patch)));

const back = ce.storage.decode(text);
if (back === undefined) logError("bad config");

10 · When it breaks

Finding out what went wrong

Three commands write to the script console, and they are marked differently there so a real problem does not look like a note to yourself: log for ordinary messages, logWarn for something odd, logError for something that failed.

Reporting an error does not stop your script — the rest of the section still runs. If you want it to stop, use your own language's way of raising an error.

onError is the safety net. Write a section with that name and it is told about any failure your script did not deal with, which is how a panel can report its own problems when nobody is watching the console. Failures are written to the console as well either way, so a broken safety net cannot hide them.

Most commands that can fail tell you by handing back false rather than by raising an error — set, saveSetting, and every component command. Checking the answer is usually simpler than catching anything.

Levels and the backstop

log("normal")
logWarn("odd, but carrying on")
logError("could not do that")

function onError(info)
  log(info.scriptId .. " failed in " .. info.phase)
end
log("normal");
logWarn("odd, but carrying on");
logError("could not do that");

function onError(info) {
  log(`${info.scriptId} failed in ${info.phase}`);
}

These are longer than the lessons and meant to be followed start to finish. 01 · A button, from nothing

The vocabulary, in one go

Ten lessons of verbs, on one control. Every line below runs — the numbers in the comments are what the calls returned, and the test suite re‑runs the whole thing.

It is a panel script on onPanelBuild: the phase that exists to build. Controls a script creates are cleared before it fires, so running it twice cannot double the layout.

Three of these steps look like a colour and are not. create() returns the name it settled on — a clash gets a suffix, so keep what it hands back rather than the name you asked for. The fill is a composite: solid, gradient, image and overlay all stack and layerOrder decides who is on top, which is why the state patches move gradientOpacity and not colour — a gradient at full opacity covers the solid layer completely, and patching underneath it stores a colour nobody ever sees. And the gradient's stops spell it color while the fill spells it colour: the gradient editor is older than the section model and kept its own spelling. Write colour in a stop and the browser is handed #undefined.

bind() answers true for a parameter nothing has declared yet, on purpose — a script may declare it later. So the guard is yours to write.

One button, by hand

local BAY, NAME, LABEL = "Bay", "Engage", "ENGAGE"

function onPanelBuild()
  -- One batch = one undo step and one re-render, however many writes are inside.
  ce.panel.batch(function()

    -- The shell. Parenting is a separate verb; the button then moves with the group.
    ce.panel.create("Group",  { name = BAY,  x = 24, y = 24, width = 320, height = 140 })
    ce.panel.create("Button", { name = NAME, x = 40, y = 52, width = 120, height = 44 })
    ce.panel.parent(NAME, BAY)

    -- Type. Ask the catalogue first: a family nobody has is REFUSED (style returns
    -- false and says why), and a non-portable face renders here but falls back
    -- after export.
    local face = ce.text.font("Segoe UI") or ce.text.font("Arial")
    ce.text.style(NAME, {
      family = face.family, size = 13, bold = true,
      letterSpacing = 0.6, justification = "centred",
    })
    set(NAME .. ".Text.content", LABEL)

    -- Size the button to its own text, through the same layout that paints it.
    local m = ce.text.measure(NAME)     -- { width = 49.8, height = 15.6, lines = 1 }
    set(NAME .. ".Transform.width", math.max(96, math.ceil(m.width) + 48))

    -- The background.
    local fill = NAME .. ".Background.Fill"
    set(fill .. ".colour", "FF1B2233")         -- `colour`: British, 8 digits AARRGGBB
    set(fill .. ".gradientEnabled", true)
    set(fill .. ".gradient", {
      type = "linear", angle = 90, edge = 0,   -- edge 0 = smooth, 100 = hard bands
      stops = {                                -- `color`: US, 6 digits RRGGBB
        { color = "2B3550", position = 0 },
        { color = "161E33", position = 100 },
      },
    })
    set(fill .. ".layerOrder", { "solid", "gradient", "image", "overlay" })

    -- The icon. The library belongs to the EDITOR, not the panel, so an icon is
    -- never portable — guard it, and let an install without it still build.
    local ico = ce.image.asset("power")
    if ico then
      ce.image.icon(NAME, ico.id, { size = 16, tint = "#E8ECF8" })
    else
      logWarn("no 'power' icon in this install — built without one")
    end

    -- The states. Patch what is actually ON TOP. patch() returns how many keys it
    -- merged, so a silent 0 is a spelling mistake you can see.
    ce.panel.patch(NAME, "Hover",    { ["Background.Fill.gradientOpacity"] = 55 })
    ce.panel.patch(NAME, "Pressed",  { ["Background.Fill.gradientOpacity"] = 20,
                                       ["Transform.scale"] = 0.94 })
    ce.panel.patch(NAME, "Disabled", { ["Transform.opacity"] = 0.4 })

    -- The synth.
    if ce.device.parameter("filter.cutoff") then
      ce.device.bind(NAME, "filter.cutoff")
    else
      logWarn("no filter.cutoff in this profile — the button is decorative")
    end
  end)
end

02 · Eight, from a table

A panel is data plus a rule

The same panel, built eight times from eight rows. The point is not that it is shorter — it is that the rule is now the thing you keep. Change COLS to 2 and the grid reflows and the group resizes with it. Add a ninth row and there is a ninth pad, coloured, labelled, wired and playing, with no other edit. A stored property can hold the result of that; nothing can store the rule.

Each piece is the language doing a different job. A table is the drum kit, kept apart from the panel. A function means eight pads that cannot drift apart the way eight copy‑pasted blocks would. Arithmetic places them and sizes the group to fit, and shade() derives every gradient's dark stop instead of you typing sixteen hex values — the API should not grow a verb for arithmetic, because every language the player embeds already has it. The label is computed from the same row that sets the rate, so the two cannot disagree.

The roll is a property, not a script. momentary/repeating is a button behaviour with a Delay and an Interval, and a script that reimplemented it with a timer would be writing a worse copy of something the control already does. What the script adds is the part a stored number cannot: the interval is derived from ce.time.division() and beatsToMs(), so the roll follows the host tempo instead of being frozen at whatever the author typed.

And the closure is the one with no property equivalent at all. Eight handlers, each holding its own row. A Value section can store a note; it cannot store "this button, that note, that velocity" eight times over.

A plain pad fires onClick once, on release. A repeating pad fires it at its own rate for as long as it is held — and not again on the way up, because the firing already happened. One handler covers both.

-- Darken a 6-digit hex. Plain Lua: this is arithmetic.
local function shade(hex, f)
  local out = ""
  for i = 0, 2 do
    local byte = tonumber(hex:sub(i * 2 + 1, i * 2 + 2), 16)
    out = out .. string.format("%02X", math.floor(byte * f))
  end
  return out
end

03 · Asking the instrument

The control knows more than your script does

Lesson 12 built a drum kit out of eight buttons, and every line of it was honest work. This is the same kit as one control, and the reason to reach for it is not that it is shorter. It is that three of the things a drum grid does cannot be built from eight independent buttons at all.

Choke groups. A closed hi‑hat silences an open one. Eight buttons cannot do that, because no button knows the others exist — you would have to write the bookkeeping yourself and keep it right as the kit changed. Strike position. Where in the pad you land decides how hard it sounds; a button has no inside. Corner zones. The four corners of every pad carry a second vocabulary — a roll under one thumb, a flam under the other — so sixteen triggers become something you can phrase on.

The overrides are sparse, and that is the interesting part. You set what differs; everything else follows the map. One fill() writes eight notes in a single document change, and the choke groups follow — nothing sets them, because a choke group is resolved from the note. Look at what the script actually stored: pad 1 holds an empty entry, because 36 is the note it was already going to play, and pinning it there would only stop it following baseNote later.

So ask, rather than tell. read() answers what the component resolved, not what you stored — so the setup can be derived. "Give a roll to every pad in a choke group" finds the hi‑hats without a single typed index, names them in the log from the same read, and keeps being right when the map, the rows or the columns change underneath it. A stored property can hold the result of that question. Nothing can store the question.

The roll is derived too: rollRate is a note value, not a number of milliseconds, so a 1/32 roll is a 1/32 against the panel tempo and stays one when the tempo moves. And rollDelay is what makes one pad do two jobs — tap it and it strikes once, lean on it and it rolls.

Corner zones are set for the grid, not per pad, on purpose: a corner is a gesture your hand learns once. Four corners meaning different things on neighbouring pads is the opposite of an instrument you can play without looking.

04 · A panel is a graph

Controls that read each other

The last three lessons built controls. This one connects them. A Meter can follow a knob, an LCD can take its value from one control and its backlight from another, an Arpeggiator can take its notes from a Chord Pad — and once any of that is true, the panel has stopped being a list of controls and become a graph.

You name the control, not its id. The field underneath stores an id, because that is what survives a rename; a script never sees one. It names the control the way it names everything else, and read() hands the name back — an opaque ctl_… is not something a script could have got hold of, and not something it could do anything with.

Not every control can drive every field, and the refusal is the interesting part. Look at what happens to Title, a plain Label, in the listing: it is accepted as the LCD's backlight source and refused as the Meter's level. One control, two answers, because the two fields want different things — "is this on" can be answered by anything, "how far up is this" cannot. The verb says which: refused — it is not a knob, slider or other range control. A wiring that failed silently would look exactly like a wiring that worked until the meter sat still.

That is what makes the return value worth reading. The loop below builds a chain from a table of intended connections and counts the ones that took, so a panel assembling itself against a kit somebody else laid out can adapt instead of half-working.

And then it reads the graph back. The last block walks the panel with ce.panel.each, asks ce.panel.info what each control IS, and asks each one what drives it. Nothing in that block knows what the first two blocks did — it would report a panel a script never built, wired entirely by hand in the inspector. Asking a stored property what it is connected to is not a thing you can do; the connection is stored, the question is not.

Naming no control unlinks, which is the inspector's own “— Static / bound —” and a real setting rather than the absence of one. A link whose target has been deleted reads back as unlinked too: the component is running on its static value either way, and that is the honest answer.

What changed

Newest first

The number of commands roughly tripled over these releases. Six of them added nothing new at all: they were corrections, where something had been quietly doing the wrong thing.

  1. ImagesPictures on a control

    Eight commands for the pictures a control can carry — a background image, an overlay, a picture or texture inside the text, and the icon it shows — plus a way to see what is in the icon library.

    Three things here are easy to get wrong, so the commands handle them for you. Background pictures stack on top of one another, while a picture inside text replaces whatever was there — so setting one up the wrong way leaves you with a layer that is fully configured and completely invisible. The word fill means "crop to fit" on a background and "stretch to fit" on text. And an icon from your library lives on this computer rather than in the panel, so it will not travel; embed copies it in so that it does.

  2. DrawingDrawing on a control

    Eleven more drawing commands: grids, sets of lines and points, smooth curves, polygons, images, clipping, blending, and a way to group a run of drawing together.

    The bigger change is speed. Anything worth drawing — a waveform, a set of tick marks, a grid of steps — means drawing the same thing many times over, and that used to get dramatically slower the more you drew. Drawing 256 line segments took longer than a single frame allows, before anything appeared on screen. Grids, lines and points are now one command for the whole set, and batch groups a run of drawing into one update — around fourteen times faster for those 256 segments.

  3. ChecksumsChecksums that agree with each other

    Many synths expect a checksum at the end of a message, and there are several ways of working one out. Scripts knew three of them and device profiles knew a different two, under different names — so a script could produce a checksum no profile could describe, and a synth using anything unusual could not have a working profile at all.

    Both now read the same list of eleven, so they cannot disagree. Ask for one that is not on the list and you get nothing back, with a message saying what is available, rather than a checksum for the wrong synth. Found along the way, and worse: while you were building a profile the editor and the finished export worked checksums out differently, so the preview was wrong and the export was right — the least helpful way round for that to be.

  4. This pageThis page

    A worked example for every command, the options written out as a table instead of described in passing, and the description moved under the name rather than into a column you had to scroll sideways to read.

    Generating the examples' answers instead of typing them turned up two commands whose descriptions were misleading: blend looked as though it took two numbers when it takes two lists, and passing numbers returned an empty list, which is correct and baffling.

  5. TextText and fonts

    Seven commands for typography: which fonts exist, what a font can do, setting a control's text style, measuring text, and shrinking it to fit.

    None of this is newly possible — every text setting could already be changed directly. What was missing was knowing which fonts are really available, keeping the two places boldness is stored in agreement, and being able to measure a control's own text in its own font.

  6. ComponentsComponents can tell you what they are doing

    Eleven things a component now reports: a step playing, a cycle completing, a pad hit or released, a scene or stage changing, a value settling, a bounce, a recall, a zone, a voicing.

    Before this a script could drive every setting of a component and never be told anything back.

  7. ComponentsEvery component setting reachable

    The component commands went from 229 to 302. Every component gained read, so you can ask what it is set to; the ones holding lists gained ways to count, replace, add and remove items; and every command now tells you whether it worked.

    A real bug turned up here. Most of the settings offering a fixed choice of values were offering the wrong ones — the arpeggiator accepted a pattern it has never had, and refused "chord", which it does have. The choices now come from the same list each component itself reads.

  8. StorageSaved settings that do not collide

    Settings gained the three scopes described in the manual, so two scripts saving something under the same name no longer overwrite each other without saying so, plus a way to store structured values as text.

  9. PanelArranging controls from a script

    Twenty-seven ways of aligning and distributing controls existed on the canvas right-click menu and nowhere else. The menu and your script now call exactly the same ones.

  10. DrawingGradients, dashes and colour

    Gradients, dashed lines, transparency and transforms as well as flat shapes, the panel's own LCD font, a way to measure text — and eight colour commands taken from the app's own, so a colour your script lightens matches the border next to it.

  11. DialogsAsking a question, not just making a statement

    A script could tell somebody something; now it can ask. A choice between buttons, a line of text, or a pick from a list.

  12. AnimationMovement that matches the panel

    Seven more ways to move a value over time. The curves are now worked out from the very same shapes the Properties panel stores, rather than from formulas that merely looked similar.

  13. TimeThe transport's own grid

  14. MusicScales, chords and voicing

    Scales, chords, voice leading and arpeggio ordering — the musical working-out the Chord Pad and Harmoniser already did internally, which a script could not reach.
