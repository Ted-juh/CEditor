Panel scripting

Write a script once. It runs in five places.

A CEditor panel can carry scripts in Lua, JavaScript, TypeScript, Python or C‑family source. They call one API. The editor runs it in a WebView while you design; the exported plugin runs the same script in an embedded engine with the window shut. The rule the whole contract is built around is that those must not differ — if it behaves one way while you are testing it, it behaves that way in the export.

Part one · the manual

Ten things, in the order you need them

01 · What a script is

A file of named functions

You do not call into CEditor and wait. You define functions with particular names, and the panel calls them when something happens. A script attached to a knob and named for onValueChanged runs every time that knob settles.

Everything in the API is a plain global function. set, get and log are always there. Everything else lives in a module you switch on — see Modules — and each module member has two spellings: a readable namespaced one (ce.midi.sendCC) and a flat global (sendCC). They are the same function.

There is no import, no require, no build step. A panel declares its modules and the runtime injects them before your first line runs.

A knob that sends a CC

function onValueChanged(value)
  sendCC(1, 74, value)
  log("cutoff", value)
end
function onValueChanged(value) {
  sendCC(1, 74, value);
  log("cutoff", value);
}

02 · Addressing

Everything has a dot‑path, rooted on a name

A control is addressed by the name you gave it, not by an id you never see. From there the path walks into whatever you want: its value, its colour, a section property.

A bare control name means its value, so get("cutoff") and get("cutoff.value") are the same question. Rename a control in the editor and every script that mentions it is updated with it.

A value has three faces. .value is the real one, .normalizedValue is its 0–1 position, and .midiValue is what goes on the wire. Suffix the path, or pass the form as a second argument.

set returns whether it wrote. A path that resolves to nothing is a typo, and it used to fail in complete silence.

Reading and writing

local hz = get("cutoff")
local pos = get("cutoff", "normalizedValue")

set("cutoff.value", 8000)
set("cutoff.normalizedValue", 0.5)
set("led.background.fill.colour", "#39D98A")

if not set("cutof.value", 1) then
  logError("no control called that")
end
const hz = get("cutoff");
const pos = get("cutoff", "normalizedValue");

set("cutoff.value", 8000);
set("cutoff.normalizedValue", 0.5);
set("led.background.fill.colour", "#39D98A");

if (!set("cutof.value", 1)) {
  logError("no control called that");
}

03 · Writing and the synth

A write usually transmits. It knows when not to.

Setting a control normally behaves as if somebody moved it: the panel updates and the synth is told. That is what you want almost always.

The exception is when you are reacting to something the synth just sent. Echoing it back is a feedback loop, so a write made inside an inbound handler is silent automatically. You do not set a flag; the runtime tracks where the write came from.

Override it with a block when you need to. An init‑patch button writes forty controls and should send none of them until it is done; a MIDI‑learn confirmation needs to send from inside an inbound handler. Both auto‑reset at the end of the block, so they cannot leak even if something throws.

Scoped, not per‑line

noTransmit(function()
  set("cutoff.value", 8000)
  set("reso.value", 40)
end)

transmit(function()
  sendCC(1, 74, 64)
end)
noTransmit(() => {
  set("cutoff.value", 8000);
  set("reso.value", 40);
});

transmit(() => {
  sendCC(1, 74, 64);
});

04 · Reacting

Name a function, or subscribe to anything

For a control's own events, define the handler by name: onValueChanged, onClick, onNoteIn. For anything else — another control, the transport, a component — use on(target, event, fn). "*" subscribes to every target, which is why every payload carries the one it came from.

There are two flavours of value change and the difference matters: onValueChange fires continuously while a knob is moving (use it for the GUI), onValueChanged fires once when it settles (use it to transmit).

watch is the third way, and it is not an event at all: it re-runs when a path changes, including nested properties no event covers.

Either spelling works in on — the event's id ("step") or its handler name ("onStep"). Only the second used to.

Three ways to be told

function onValueChanged(value)
  sendCC(1, 74, value)
end

on("*", "onStep", function(step)
  set(step.target .. ".led", true)
end)

watch("cutoff.background.fill.colour", function(c)
  log("colour is now", c)
end)
function onValueChanged(value) {
  sendCC(1, 74, value);
}

on("*", "onStep", (step) => {
  set(step.target + ".led", true);
});

watch("cutoff.background.fill.colour", (c) => {
  log("colour is now", c);
});

05 · Modules

You pay for what you switch on

The surface is 555 members across 41 modules. Injecting all of it into every panel would be wasteful, so a panel declares the modules it uses and the export carries only those. The weights in What it weighs are measured from the real preludes, not estimated.

ce.core is always on and never namespaced — set and get have no prefix. Every other module gives you both spellings.

A member from a module you did not declare returns nothing and says so in the console. It does not throw, and it does not silently do nothing.

Nine modules are cross-runtime; the rest are panel view only, which means they need the window open. Drawing, dialogs and the component families are in the second group because with the window shut there is no surface, nobody to ask, and no component engine running.

Two spellings, one function

-- ce.core is global
set("cutoff.value", 8000)

-- everything else, either way
ce.midi.sendCC(1, 74, 64)
sendCC(1, 74, 64)

local n = ce.music.quantize(63, 60, "minor")
local m = quantizeNote(63, 60, "minor")
// ce.core is global
set("cutoff.value", 8000);

// everything else, either way
ce.midi.sendCC(1, 74, 64);
sendCC(1, 74, 64);

const n = ce.music.quantize(63, 60, "minor");
const m = quantizeNote(63, 60, "minor");

06 · Musical time

Beats, not milliseconds

ce.time reads the transport — the editor's clock, or the DAW playhead when the window is shut — and converts between beats and milliseconds at the current tempo. The delay‑time calculation every synth panel needs is one call.

Timers come in three shapes: startTimer repeats, after fires once, and syncTimer repeats on a musical interval and follows the tempo when it changes.

onBeat and onBar are watched on the message thread at about 30 Hz. That lands within a frame of the beat — right for lighting an LED or stepping a sequencer, wrong for anything that has to be sample‑accurate.

Settle, then send

sendProgramChange(1, 12)
ce.time.after(40, function()
  sendDump("patch")
end)

local ms = ce.time.beatsToMs(0.75)
set("delayTime.value", ms)

ce.time.syncTimer("step", 0.25)
function onTimer(info)
  if info.id == "step" then step() end
end
sendProgramChange(1, 12);
ce.time.after(40, () => {
  sendDump("patch");
});

const ms = ce.time.beatsToMs(0.75);
set("delayTime.value", ms);

ce.time.syncTimer("step", 0.25);
function onTimer(info) {
  if (info.id === "step") step();
}

07 · Components

Drive the arpeggiator, and hear back from it

The interactive components — arpeggiator, chord pad, sequencers, matrix, envelope, displays — each get a module of verbs. Every verb takes the control's name first, and every one returns whether the component now holds what you asked for. A value it does not have is refused, not stored.

read asks what a component is set to, in the same words the verbs use. size, fill, insert and remove work on the lists a component carries — steps, nodes, breakpoints, destinations.

And they raise events: a step firing, a scene changing, a pad struck, a take finishing. Those are panel‑view only, because the component engines run in the editor's surface.

Ask, set, react

if not ce.components.arp.pattern(a, "chord") then
  logError("that pattern does not exist")
end

local now = ce.components.arp.read(a, "pattern")
local n = ce.components.turing.size(t, "step")
ce.components.turing.fill(t, "step", {0, 0.5, 1, 0.25})

on(a, "onStep", function(step)
  log("step " .. step.index .. " of " .. step.of)
end)
if (!ce.components.arp.pattern(a, "chord")) {
  logError("that pattern does not exist");
}

const now = ce.components.arp.read(a, "pattern");
const n = ce.components.turing.size(t, "step");
ce.components.turing.fill(t, "step", [0, 0.5, 1, 0.25]);

on(a, "onStep", (step) => {
  log(`step ${step.index} of ${step.of}`);
});

08 · Typography

The fields were never the problem

Text.Font has 41 fields, Text.Multiline eleven and Text.Position around forty — and set() could always write every one of them by path. set("L.Text.Font.size", 18) has worked since the first release. So ce.text adds no reach. It adds the three things a bare path write cannot do.

It knows what exists. fonts() is the catalogue the Properties panel picks from; font(family) is one entry or nothing. A family nobody has is refused rather than stored — where set() would keep the typo and quietly fall back to a platform default. Read portable before you commit to a face: a builtin is named in every runtime, while a font from the library belongs to this editor install and is not part of the panel document, so it looks right while you build and falls back once exported.

It keeps the invariants. weight and weightValue are a pair, and two different consumers read different halves — the renderer takes weightValue first, the Properties panel reads weight for a non‑variable face. Writing one alone makes the editor and the render disagree, in both directions. style() always writes both, and axis("wght", …) drags the pair along with it.

It can measure itself. measure() reports what a control's text occupies in its own font, through the same layout function that paints it — no size or family handed in, and letter spacing, wrapping and maxLines all honoured. fit() then shrinks Font.size until it fits the box and tells you what it chose. fitMode = "shrink" already scales text down when painting, but that is a paint‑time scale: the stored size never changes, so nothing can ask what it settled on. fit() writes a number other layout can use.

Panel view only, and deliberately: the catalogue is the editor's and the measuring wants a canvas. A typography verb answering from a guess would be worse than one that says it is not there.

Check, style, fit

local face = ce.text.font("Inter Tight")
if not face or not face.portable then
  face = ce.text.font("Arial")     -- survives the export
end

ce.text.style("Readout", {
  family = face.family, size = 18,
  bold = true, tabularFigures = true,
})

if face.variable then
  ce.text.axis("Readout", "wght", 620)
end

set("Readout.Text.content", patchName)
local fitted = ce.text.fit("Readout", { min = 9 })
if not fitted.fits then
  logWarn("still overflowing at " .. fitted.size)
end
let face = ce.text.font("Inter Tight");
if (!face || !face.portable) {
  face = ce.text.font("Arial");    // survives the export
}

ce.text.style("Readout", {
  family: face.family, size: 18,
  bold: true, tabularFigures: true,
});

if (face.variable) {
  ce.text.axis("Readout", "wght", 620);
}

set("Readout.Text.content", patchName);
const fitted = ce.text.fit("Readout", { min: 9 });
if (!fitted.fits) {
  logWarn(`still overflowing at ${fitted.size}`);
}

09 · Keeping things

Three lifespans, and you pick

state is a plain table of your own that survives between handler calls and dies when the script reloads. Use it for anything you are counting.

Settings outlive the session, and they have three scopes. "panel" is shared by every script on the panel and travels with the document. "script" is private to yours. "local" never enters the document at all — a panel you send somebody should not carry your MIDI port choice.

encode and decode are JSON, and they are here rather than in your language because one of the five runtimes has none: the Lua engine opens base, math, string and table. All five produce identical text for identical values, keys sorted, so two structures can be compared by comparing their encodings.

Scratch, saved, shipped

state.hits = (state.hits or 0) + 1

ce.storage.saveSetting("bank", 3)
ce.storage.saveSetting("port", "IAC",
                       { scope = "local" })

local patch = { name = "Lead", cutoff = 0.75 }
sendSysex(toAscii(ce.storage.encode(patch)))

local back = ce.storage.decode(text)
if back == nil then logError("bad config") end
state.hits = (state.hits ?? 0) + 1;

ce.storage.saveSetting("bank", 3);
ce.storage.saveSetting("port", "IAC",
                       { scope: "local" });

const patch = { name: "Lead", cutoff: 0.75 };
sendSysex(toAscii(ce.storage.encode(patch)));

const back = ce.storage.decode(text);
if (back === undefined) logError("bad config");

10 · When it breaks

Three levels, and a handler for the rest

log, ce.core.warn and ce.core.error land at different levels in the script console, so a real failure does not read like a debug print. Note the flat spellings are logWarn and logError: a global called error would shadow Lua's builtin and turn the standard way to raise into a print.

Reporting an error does not stop the handler. To actually stop, raise with your own language's error / throw.

onError catches what a script did not: the failure is always logged as well, so a panel whose own error handler is broken does not go quiet.

Verbs that can fail say so in their return value rather than throwing — set, saveSetting, and every component verb. Checking one is usually cheaper than a handler.

Levels and the backstop

log("normal")
logWarn("odd, but carrying on")
logError("could not do that")

function onError(info)
  log(info.scriptId .. " failed in " .. info.phase)
end
log("normal");
logWarn("odd, but carrying on");
logError("could not do that");

function onError(info) {
  log(`${info.scriptId} failed in ${info.phase}`);
}

11 · A button, from nothing

The vocabulary, in one go

Ten lessons of verbs, on one control. Every line below runs — the numbers in the comments are what the calls returned, and the test suite re‑runs the whole thing.

It is a panel script on onPanelBuild: the phase that exists to build. Controls a script creates are cleared before it fires, so running it twice cannot double the layout.

Three of these steps look like a colour and are not. create() returns the name it settled on — a clash gets a suffix, so keep what it hands back rather than the name you asked for. The fill is a composite: solid, gradient, image and overlay all stack and layerOrder decides who is on top, which is why the state patches move gradientOpacity and not colour — a gradient at full opacity covers the solid layer completely, and patching underneath it stores a colour nobody ever sees. And the gradient's stops spell it color while the fill spells it colour: the gradient editor is older than the section model and kept its own spelling. Write colour in a stop and the browser is handed #undefined.

bind() answers true for a parameter nothing has declared yet, on purpose — a script may declare it later. So the guard is yours to write.

One button, by hand

local BAY, NAME, LABEL = "Bay", "Engage", "ENGAGE"

function onPanelBuild()
  -- One batch = one undo step and one re-render, however many writes are inside.
  ce.panel.batch(function()

    -- The shell. Parenting is a separate verb; the button then moves with the group.
    ce.panel.create("Group",  { name = BAY,  x = 24, y = 24, width = 320, height = 140 })
    ce.panel.create("Button", { name = NAME, x = 40, y = 52, width = 120, height = 44 })
    ce.panel.parent(NAME, BAY)

    -- Type. Ask the catalogue first: a family nobody has is REFUSED (style returns
    -- false and says why), and a non-portable face renders here but falls back
    -- after export.
    local face = ce.text.font("Segoe UI") or ce.text.font("Arial")
    ce.text.style(NAME, {
      family = face.family, size = 13, bold = true,
      letterSpacing = 0.6, justification = "centred",
    })
    set(NAME .. ".Text.content", LABEL)

    -- Size the button to its own text, through the same layout that paints it.
    local m = ce.text.measure(NAME)     -- { width = 49.8, height = 15.6, lines = 1 }
    set(NAME .. ".Transform.width", math.max(96, math.ceil(m.width) + 48))

    -- The background.
    local fill = NAME .. ".Background.Fill"
    set(fill .. ".colour", "FF1B2233")         -- `colour`: British, 8 digits AARRGGBB
    set(fill .. ".gradientEnabled", true)
    set(fill .. ".gradient", {
      type = "linear", angle = 90, edge = 0,   -- edge 0 = smooth, 100 = hard bands
      stops = {                                -- `color`: US, 6 digits RRGGBB
        { color = "2B3550", position = 0 },
        { color = "161E33", position = 100 },
      },
    })
    set(fill .. ".layerOrder", { "solid", "gradient", "image", "overlay" })

    -- The icon. The library belongs to the EDITOR, not the panel, so an icon is
    -- never portable — guard it, and let an install without it still build.
    local ico = ce.image.asset("power")
    if ico then
      ce.image.icon(NAME, ico.id, { size = 16, tint = "#E8ECF8" })
    else
      logWarn("no 'power' icon in this install — built without one")
    end

    -- The states. Patch what is actually ON TOP. patch() returns how many keys it
    -- merged, so a silent 0 is a spelling mistake you can see.
    ce.panel.patch(NAME, "Hover",    { ["Background.Fill.gradientOpacity"] = 55 })
    ce.panel.patch(NAME, "Pressed",  { ["Background.Fill.gradientOpacity"] = 20,
                                       ["Transform.scale"] = 0.94 })
    ce.panel.patch(NAME, "Disabled", { ["Transform.opacity"] = 0.4 })

    -- The synth.
    if ce.device.parameter("filter.cutoff") then
      ce.device.bind(NAME, "filter.cutoff")
    else
      logWarn("no filter.cutoff in this profile — the button is decorative")
    end
  end)
end

-- Motion. A spring for the press, because it should settle rather than snap;
-- a tween for the glow, because it has a length you want to name.
on(NAME, "pointerDown", function()
  ce.anim.spring(NAME .. ".Transform.scale", 0.94, { damping = 8, frequency = 14 })
end)

on(NAME, "pointerUp", function()
  ce.anim.spring(NAME .. ".Transform.scale", 1.0, { damping = 8, frequency = 14 })

on(NAME, "valueChanged", function(v)

12 · Eight, from a table

A panel is data plus a rule

The same panel, built eight times from eight rows. The point is not that it is shorter — it is that the rule is now the thing you keep. Change COLS to 2 and the grid reflows and the group resizes with it. Add a ninth row and there is a ninth pad, coloured, labelled, wired and playing, with no other edit. A stored property can hold the result of that; nothing can store the rule.

Each piece is the language doing a different job. A table is the drum kit, kept apart from the panel. A function means eight pads that cannot drift apart the way eight copy‑pasted blocks would. Arithmetic places them and sizes the group to fit, and shade() derives every gradient's dark stop instead of you typing sixteen hex values — the API should not grow a verb for arithmetic, because every language the player embeds already has it. The label is computed from the same row that sets the rate, so the two cannot disagree.

The roll is a property, not a script. momentary/repeating is a button behaviour with a Delay and an Interval, and a script that reimplemented it with a timer would be writing a worse copy of something the control already does. What the script adds is the part a stored number cannot: the interval is derived from ce.time.division() and beatsToMs(), so the roll follows the host tempo instead of being frozen at whatever the author typed.

And the closure is the one with no property equivalent at all. Eight handlers, each holding its own row. A Value section can store a note; it cannot store "this button, that note, that velocity" eight times over.

A plain pad fires onClick once, on release. A repeating pad fires it at its own rate for as long as it is held — and not again on the way up, because the firing already happened. One handler covers both.

The rule

-- Darken a 6-digit hex. Plain Lua: this is arithmetic.
local function shade(hex, f)
  local out = ""
  for i = 0, 2 do
    local byte = tonumber(hex:sub(i * 2 + 1, i * 2 + 2), 16)
    out = out .. string.format("%02X", math.floor(byte * f))
  end
  return out
end

-- One pad, from one row of the table.
local function buildPad(part, index)
  local col = (index - 1) % COLS
  local row = math.floor((index - 1) / COLS)

  local name = ce.panel.create("Button", {
    name = "pad" .. part.note,
    x = PAD + col * (W + GAP),
    y = PAD + row * (H + GAP),
    width = W, height = H,
  })

  -- The label is COMPUTED, so a roll pad says so without anyone typing it twice.
  local label = string.upper(part.name)
  if part.roll then label = label .. "  " .. part.roll.rate end

  ce.text.style(name, { family = "Arial", size = 11, bold = true, letterSpacing = 0.4 })

13 · Asking the instrument

The control knows more than your script does

Lesson 12 built a drum kit out of eight buttons, and every line of it was honest work. This is the same kit as one control, and the reason to reach for it is not that it is shorter. It is that three of the things a drum grid does cannot be built from eight independent buttons at all.

Choke groups. A closed hi‑hat silences an open one. Eight buttons cannot do that, because no button knows the others exist — you would have to write the bookkeeping yourself and keep it right as the kit changed. Strike position. Where in the pad you land decides how hard it sounds; a button has no inside. Corner zones. The four corners of every pad carry a second vocabulary — a roll under one thumb, a flam under the other — so sixteen triggers become something you can phrase on.

The overrides are sparse, and that is the interesting part. You set what differs; everything else follows the map. One fill() writes eight notes in a single document change, and the choke groups follow — nothing sets them, because a choke group is resolved from the note. Look at what the script actually stored: pad 1 holds an empty entry, because 36 is the note it was already going to play, and pinning it there would only stop it following baseNote later.

So ask, rather than tell. read() answers what the component resolved, not what you stored — so the setup can be derived. "Give a roll to every pad in a choke group" finds the hi‑hats without a single typed index, names them in the log from the same read, and keeps being right when the map, the rows or the columns change underneath it. A stored property can hold the result of that question. Nothing can store the question.

The roll is derived too: rollRate is a note value, not a number of milliseconds, so a 1/32 roll is a 1/32 against the panel tempo and stays one when the tempo moves. And rollDelay is what makes one pad do two jobs — tap it and it strikes once, lean on it and it rolls.

Corner zones are set for the grid, not per pad, on purpose: a corner is a gesture your hand learns once. Four corners meaning different things on neighbouring pads is the opposite of an instrument you can play without looking.

14 · A panel is a graph

Controls that read each other

The last three lessons built controls. This one connects them. A Meter can follow a knob, an LCD can take its value from one control and its backlight from another, an Arpeggiator can take its notes from a Chord Pad — and once any of that is true, the panel has stopped being a list of controls and become a graph.

You name the control, not its id. The field underneath stores an id, because that is what survives a rename; a script never sees one. It names the control the way it names everything else, and read() hands the name back — an opaque ctl_… is not something a script could have got hold of, and not something it could do anything with.

Not every control can drive every field, and the refusal is the interesting part. Look at what happens to Title, a plain Label, in the listing: it is accepted as the LCD's backlight source and refused as the Meter's level. One control, two answers, because the two fields want different things — "is this on" can be answered by anything, "how far up is this" cannot. The verb says which: refused — it is not a knob, slider or other range control. A wiring that failed silently would look exactly like a wiring that worked until the meter sat still.

That is what makes the return value worth reading. The loop below builds a chain from a table of intended connections and counts the ones that took, so a panel assembling itself against a kit somebody else laid out can adapt instead of half-working.

And then it reads the graph back. The last block walks the panel with ce.panel.each, asks ce.panel.info what each control IS, and asks each one what drives it. Nothing in that block knows what the first two blocks did — it would report a panel a script never built, wired entirely by hand in the inspector. Asking a stored property what it is connected to is not a thing you can do; the connection is stored, the question is not.

Naming no control unlinks, which is the inspector's own “— Static / bound —” and a real setting rather than the absence of one. A link whose target has been deleted reads back as unlinked too: the component is running on its static value either way, and that is the honest answer.

What changed

The last fourteen phases, newest first

The surface roughly tripled over these. Six of them were not additions at all — they were the API telling the truth about things it had been quietly getting wrong.

  1. §50ce.image

    Eight verbs for the image layers a control carries — background image and overlay, text image and texture, and the Icon section — plus the icon library they draw from. Like ce.text, this adds no reach: a Label has 102 image‑related fields and a Knob 864, and every one was already writable by path while nothing in the API named a single one.

    What it adds is three things reading the renderer turned up. There are two activation models: background layers composite through layerOrder, while text layers are exclusive and the renderer switches on mode rather than on Enabled — so a layer can be fully configured and invisible. There are two fit vocabularies under one name, and fill means cover on a background and stretch on text. And there are three source models with different portability: a data URL travels with the panel, a file path is machine‑local and resolved asynchronously, and an icon‑library reference lives in app settings. embed() collapses the last two into the first, which nothing else in the app can do.

  2. §49ce.draw

    16 → 27 members: grid, lines, points, curve, polygon, image, clip, blend, save, restore and batch, plus dashOffset on stroke.

    The verb count was never the problem: the module could not afford a loop. Every command republished the whole command list, so drawing n shapes was O(n²) work and n re‑renders — 256 line segments cost 21ms before any painting happened, more than a 60fps frame. And every interesting drawing (a scope trace, a spectrum, a step grid, tick marks) is a loop. The list is no longer copied per command; grid, lines and points are one command for the whole lot; and batch collapses a run into a single publish — measured at 14× faster for 256 segments and 19× for a 128×128 grid. A test pins the ratio so the quadratic cannot come back.

  3. §48checksums

    ce.midi.checksum knew three algorithms; the device profile engine knew a different two, under different names, and hard‑rejected the rest. So a script could compute a checksum no profile could express, and a synth using anything but Roland's or a plain sum could not have a working profile at all. Both read one table now — eleven algorithms, including one’s complement, the Kawai‑shaped constant offset (the constant is yours to give), and CRC‑8/16/32 with the two CRC‑16 variants named separately, because “crc16” alone is not a specification. An unknown name now returns nothing instead of a Roland checksum.

    Found on the way, and worse than the gap: the editor and the export computed recipe checksums differently. The web fallback — which runs in the browser and in the DPD while you are writing a profile — clamped where it should have masked (so almost every message produced exactly 127), summed the header along with the data, ignored the declared algorithm entirely, and dropped $address and $size on the floor. Its own verify path would have rejected what its build path produced. The preview lied and the export was correct, which is the worst direction for a bug like this to run.

  4. §47this page

    A worked example for all 536 members, the declared opts fields shown rather than described, and the member layout restacked so the description sits under the identifiers instead of in a fourth column you had to scroll sideways to read.

    Found on the way, by generating the examples' results instead of typing them: blend's signature read blend(a, b, t) with no hint that both are LISTS — passing two numbers returns an empty list, which is correct and baffling — and decodeJson never documented that JSON null reads as nothing, so encode‑then‑decode is not always identity. Two narrow‑screen layout bugs turned up too: the changelog's own two columns never collapsed, leaving each entry 122px to hold a paragraph in.

  5. §46ce.text

    Seven verbs for typography: fonts, font, style, axis, read, measure, fit. The unusual thing about this module is that it adds no reach — all ninety‑odd text fields were already writable by path. What was missing was knowing which fonts exist, keeping weight and weightValue consistent, and being able to measure a control's own text in its own font.

    Found on the way: the warning for a mistyped field on a fixed‑shape section had been dead code since it was written. It hung off the wrong branch of an if, testing for a state that branch could never be in — so set("L.Text.Font.sze", 20) stored a key nothing reads and said nothing at all. It fires now, on both the editor and the player path, because whether a key is new on a typed section is a question about the control, not about who writes it.

  6. §45ce.components events

    Eleven events, so a script can hear back: onStep, onCycle, onHit, onRelease, onScene, onStage, onSettled, onBounce, onRecall, onZone, onVoiced. Before this a script could drive 302 component members and never be told anything.

    Found on the way: on(target, event, fn) only ever matched the handler name, while the events list names events by id — so on("*", "timer", fn) registered a listener that could never fire, silently, since the verb existed. Both spellings work now.

  7. §44ce.components

    229 → 302 members. Every family gained read; the ones with lists gained size, fill, and where an element has a template, insert and remove. Every verb now reports whether it applied.

    And a real bug: 24 of the 28 enum verbs offered values no component has and refused values it does. arp.pattern accepted "converge", which the arpeggiator has never had, and refused "chord", which it does. arp.division offered eight of the transport's fourteen note values while ce.time.divisions() — same panel, same script — already answered from all fourteen. The values now come from the table each component's own code reads.

  8. §43ce.storage

    5 → 10 members. Three scopes, so two scripts saving "count" no longer clobber each other in silence, plus JSON — which exists because the Lua engine has none and all five runtimes must produce identical text.

  9. §42ce.panel

    15 → 24. Twenty-seven alignment operations sat on the canvas context menu and were reachable from nothing else; they are pure functions now, and the menu and the script call the same ones.

  10. §41ce.draw & colour

    Gradients, dashes, opacity, transforms, the panel's own LCD font, text measurement — and eight colour verbs in ce.math, ported from the app's own so a script-lightened colour matches the border beside it.

  11. §40ce.ui

    3 → 9. Ask a question rather than only make a statement: a choice, a line of text, a pick from a list — as dialog shapes, not three more modals.

  12. §39ce.anim

    4 → 11. A real cubic-bezier solver in all four runtimes rather than four lookalike formulas: the panel stores CSS control points, and 1-(1-t)² is not cubic-bezier(.25,.46,.45,.94).

  13. §38ce.time

    9 → 22. The transport's own grid — divisions, bar/beat, swing, loop folding, tempo from taps. Lua had no clock at all: it opens base, math, string and table, so there was no os.clock to call.

  14. §37ce.music

    5 → 13. Scales, chords, voice leading, arp order — the maths the Chord Pad and Harmoniser already did internally, which a script could not reach. noteNumber could not read a flat and returned 0 for anything it failed on, which is a real note.
