# Device Profile Engine MVP Plan

This document defines the first implementation plan for CEditor's device profile and MIDI layer.

The important architectural decision is:

> CEditor should not build a SysEx generator. It should build a device intent compiler.

A panel component should emit a semantic intent:

```text
Set mainSynth.filter.cutoff to 64
```

The device layer decides whether that intent becomes SysEx, CC, NRPN, RPN, Program Change, a multi-message transaction, a delayed sequence, or a no-op because the parameter is read-only.

## Architectural Principle

```text
A panel component never owns synth implementation logic.
A device profile never owns visual layout.
A binding connects a component port to a semantic device parameter.
The backend compiles semantic device intents into MIDI transactions.
```

This keeps the panel builder, device definitions, and live MIDI runtime separate.

## Internal Names

Use broad internal names. Avoid making "SysEx" the center of the architecture.

```text
Panel Builder
  Visual editor, controls, layout, styles, pages, component ports.

Device Profile Engine
  Device definitions, parameters, value model, encoders, checksums, validation, transaction compilation.

Device Runtime
  Device roles, state cache, MIDI destinations, MIDI queue, feedback suppression, monitor events.

Device Profile Designer
  Authoring UI for .ceditor-device files. This comes after the backend spine is stable.
```

## MVP Goal

The first useful version is complete when this flow works:

```text
1. Load a device profile.
2. Create or select a device role called mainSynth.
3. Select a MIDI destination.
4. Open the parameter browser.
5. Drag Filter Cutoff onto a knob/slider.
6. The control adopts label, range, default value, and display metadata.
7. Moving the control updates UI state immediately.
8. The frontend sends a semantic setParameter intent to the backend.
9. The backend validates the value.
10. The backend compiles a MIDI transaction.
11. MIDI preview shows the generated bytes.
12. The runtime queue sends safely, or dry-run mode logs without sending.
13. MIDI monitor logs the result.
14. A second control bound to the same parameter updates from backend state.
15. A test vector for that parameter passes.
```

Anything outside that flow is deferred unless it directly protects the spine.

## Current Implementation Status

Implemented:

- Declarative `.ceditor-device` JSON profiles for internal CC, SysEx, and NRPN test devices.
- Backend Device Profile Engine with semantic parameter compilation, value encoding, checksum support, validation messages, and test vectors.
- First-class MIDI transactions with message bytes, policy metadata, and monitor-friendly fields.
- Device Runtime service with role-to-profile mapping, runtime state cache, dry-run preview, JUCE MIDI destination discovery, opt-in hardware sending, and queue/rate-limit coalescing.
- Bridge APIs for profile listing, parameter listing, destination listing, preview, set-parameter, runtime state, monitor events, diagnostics, raw MIDI preview/actions, and profile tests.
- Frontend Device tab with profile/destination selection, parameter compatibility checks, binding creation, metadata adoption, transaction preview, test summary, monitor, and diagnostics.
- Device Bindings section on components, including default-safe dry-run behavior.
- Interaction preview emits semantic set-parameter intents for bound control ports.

Still incomplete:

- Backend-originated state fan-out to all controls bound to the same parameter.
- Incoming MIDI parsing, echo suppression, dump request/response handling, and feedback-loop testing.
- Persistent project-level role/destination/profile mapping.
- External profile import/loading outside bundled internal test profiles.
- Full async queue worker with delayed message spacing per individual message.
- Device Profile Designer authoring UI.

## Canonical Parameter Value Model

Every parameter can move through several value forms:

```text
Displayed value
  What the user sees or edits.

Semantic value
  The logical value CEditor stores and validates.

Normalized value
  Usually 0.0-1.0 for generic controls.

Encoded MIDI value
  7-bit, 14-bit, enum number, text bytes, packed bits, etc.

Raw bytes
  Final bytes sent to MIDI.
```

Example:

```text
Displayed value: "+12 semitones"
Semantic value: 12
Normalized value: 0.75
Encoded value: 76
Raw MIDI: B0 4A 4C
```

## Access And Capability Flags

Parameters should declare what is safe and possible.

```json
{
  "access": {
    "canRead": true,
    "canWrite": true,
    "realtimeSafe": true,
    "source": "singleParameter",
    "dumpReadable": true,
    "requiresConfirmation": false
  }
}
```

Examples:

```text
Read-only dump field
  canRead: true
  canWrite: false
  source: dumpOnly

Dangerous action
  canRead: false
  canWrite: true
  realtimeSafe: false
  requiresConfirmation: true

Slow SysEx-only parameter
  canRead: true
  canWrite: true
  realtimeSafe: false
```

The UI should use these flags for warnings, disabled actions, and compatibility messages.

## Send Policy

Profiles can define global timing defaults, but parameters need their own send policies.

Continuous parameter:

```json
{
  "sendPolicy": {
    "mode": "continuous",
    "coalesce": true,
    "minIntervalMs": 20,
    "sendFinalOnRelease": true
  }
}
```

Text or patch name:

```json
{
  "sendPolicy": {
    "mode": "onCommit",
    "coalesce": false
  }
}
```

Dangerous action:

```json
{
  "sendPolicy": {
    "mode": "explicitAction",
    "requiresConfirmation": true
  }
}
```

## Message Recipes

Parameters refer to reusable message recipes.

CC example:

```json
{
  "id": "cutoffCc",
  "kind": "cc",
  "channel": "$channel",
  "controller": 74,
  "value": "$encodedValue"
}
```

SysEx example:

```json
{
  "id": "singleParameterWrite",
  "kind": "sysex",
  "template": [
    "F0",
    "7D",
    "$deviceId",
    "$address",
    "$encodedValue",
    "$checksum",
    "F7"
  ],
  "checksum": {
    "type": "sum-7bit",
    "from": "$address",
    "to": "$encodedValue"
  }
}
```

NRPN example:

```json
{
  "id": "nrpn14",
  "kind": "nrpn",
  "channel": "$channel",
  "parameterMsb": 1,
  "parameterLsb": 32,
  "valueResolution": 14,
  "value": "$encodedValue",
  "nullAfterSend": false
}
```

## MIDI Transaction Model

Compiled output is a transaction, not a byte array.

```json
{
  "transactionId": "tx_123",
  "source": {
    "deviceRole": "mainSynth",
    "parameterId": "filter.cutoff",
    "value": 64
  },
  "messages": [
    {
      "kind": "sysex",
      "bytes": "F0 7D 10 20 40 70 F7",
      "delayAfterMs": 20
    }
  ],
  "policy": {
    "coalesce": true,
    "realtimeSafe": true,
    "dryRun": false
  },
  "preview": {
    "displayedValue": "64",
    "semanticValue": 64,
    "normalizedValue": 0.503937,
    "encodedValue": "40",
    "checksumStatus": "ok"
  }
}
```

NRPN transaction:

```json
{
  "messages": [
    { "kind": "cc", "channel": 1, "controller": 99, "value": 1 },
    { "kind": "cc", "channel": 1, "controller": 98, "value": 32 },
    { "kind": "cc", "channel": 1, "controller": 6, "value": 64 },
    { "kind": "cc", "channel": 1, "controller": 38, "value": 0 }
  ]
}
```

Future dump request transaction:

```json
{
  "messages": [
    {
      "kind": "sysex",
      "bytes": "F0 7D 10 11 00 40 F7",
      "delayAfterMs": 100
    }
  ],
  "expectsResponse": {
    "type": "sysex",
    "timeoutMs": 2000,
    "matcher": "currentPatchDump"
  }
}
```

## Device Runtime State

The backend owns the authoritative live state.

```text
DeviceRuntimeState
  role: mainSynth
  profileId: test-sysex-synth
  values:
    filter.cutoff = 64
    filter.resonance = 32
    osc.waveform = saw
```

Frontend state can be optimistic for responsiveness, but backend state is the truth.

UI flow:

```text
UI changes value
-> frontend sends setParameter intent
-> backend validates
-> backend updates runtime state
-> backend compiles transaction
-> backend queues/sends or dry-runs
-> backend emits parameterChanged and midiSent/midiPreview
-> all bound controls sync
```

Future incoming dump flow:

```text
MIDI input receives SysEx
-> backend matches profile/dump type
-> backend parses values
-> backend updates runtime state
-> frontend receives parameter updates
-> bound controls sync
```

## Feedback Loop Prevention

Reserve a feedback policy now, even if full MIDI input is deferred.

```json
{
  "feedback": {
    "receiveUpdates": true,
    "ignoreOwnEchoes": true,
    "echoWindowMs": 250
  }
}
```

Outgoing transactions should be taggable so obvious echoed messages can be ignored later.

## MIDI Destination Abstraction

Do not couple device runtime only to standalone hardware ports.

```text
hardwareOutput
pluginOutput
virtual
previewOnly
none
```

Project device instance example:

```json
{
  "role": "mainSynth",
  "profileId": "test-sysex-synth",
  "variables": {
    "deviceId": 16,
    "channel": 1
  },
  "midiDestination": {
    "type": "hardwareOutput",
    "id": "UM-One MIDI Out"
  },
  "timingOverrides": {
    "minDelayBetweenMessagesMs": 30
  }
}
```

Standalone mode can list/open hardware devices. Plugin mode can use plugin MIDI output or preview-only routing.

## Binding Types

Do not overload one binding system with every meaning.

### Device Parameter Binding

```json
{
  "kind": "deviceParameter",
  "componentId": "knob_1",
  "port": "value",
  "deviceRole": "mainSynth",
  "parameterId": "filter.cutoff",
  "adoptMetadata": true,
  "feedback": {
    "receiveUpdates": true,
    "ignoreOwnEchoes": true
  }
}
```

### Visual Runtime Binding

This is the current CEditor-style binding.

```json
{
  "kind": "visualRuntime",
  "source": "state.hover",
  "target": "Background.Fill.colour"
}
```

### Raw MIDI / Action Binding

```json
{
  "kind": "rawMidiAction",
  "componentId": "button_1",
  "event": "clicked",
  "message": "B0 7B 00"
}
```

Raw actions are useful for panic buttons, identity requests, local on/off, and one-off utility messages.

## Component Ports And Compatibility

Component metadata should declare ports.

```json
{
  "componentType": "Slider",
  "ports": [
    {
      "id": "value",
      "accepts": ["integer", "float", "bipolar"],
      "defaultBindingMode": "continuous"
    }
  ]
}
```

Initial compatibility table:

```text
Knob.value
  integer, float, bipolar, choice-stepped

Slider.value
  integer, float, bipolar

Toggle.state
  boolean, two-choice enum

Combobox.selectedChoice
  choice, enum

TextInput.text
  text, patchName

Button.trigger
  action, momentary, dumpRequest, rawMidiAction

XYPad.x / XYPad.y
  integer, float, normalized

Envelope.attack / decay / sustain / release
  integer, float, time-like parameter
```

Drag/drop outcomes:

```text
Compatible
Compatible with warning
Not compatible
```

Example warning:

```text
Filter Type is a choice parameter.
A knob can control it as a stepped selector, but a dropdown is recommended.
```

When missing:


## Validation Levels

Validation should be backend-authoritative.

```text
Error
  Profile cannot load or can produce invalid MIDI.

Warning
  Profile loads but may behave unexpectedly.

Info
  Suggestion or missing optional metadata.
```

Example errors:

```text
MIDI data byte outside 0-127
Unknown encoder
Unknown message recipe
Parameter references missing recipe
Checksum references invalid range
Invalid schema version
```

Example warnings:

```text
No test vectors
No timing policy
Parameter has no group
Choice labels missing
No firmware compatibility metadata
```

Example info:

```text
Parameter has no preferred UI component
No short label supplied
```

## Test Profiles Before Real Synths

Create small internal profiles before supporting real hardware.

```text
Test CC Synth
  filter.cutoff via CC 74
  filter.resonance via CC 71
  osc.waveform as enum CC

Test SysEx Synth
  simple header/address/value/checksum

Test NRPN Synth
  7-bit and 14-bit NRPN values
```

These profiles let the backend compiler, transaction model, test vectors, preview, state cache, and UI bindings be tested without manufacturer quirks.

After those pass, add one real proof synth.

## Backend Compiler Responsibilities

The Device Profile Engine should be able to compile without MIDI hardware.

Input:

```json
{
  "deviceRole": "mainSynth",
  "parameterId": "filter.cutoff",
  "value": 64,
  "mode": "dryRun"
}
```

Responsibilities:

```text
Resolve role to device instance.
Resolve profile and parameter.
Validate access flags.
Validate value against parameter type/range/choices.
Normalize value when needed.
Encode value.
Resolve variables.
Compile message recipe.
Compute checksums.
Build transaction.
Apply send policy.
Run dry-run or queue send.
Update runtime state when valid.
Emit preview, monitor, and parameterChanged events.
```

## MIDI Monitor MVP

The monitor should be part of the spine.

Minimum fields:

```text
Timestamp
Direction: in/out/error/preview
Device role
Destination/source
Message type
Semantic meaning
Hex

```

Examples:

