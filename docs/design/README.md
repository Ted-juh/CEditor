# Design records

Design records for the editor and its tooling. These are **not** user documentation — they are
the decisions, the reasoning behind them, and the plans that carried them out. User-facing docs
live in [`docs/`](../README.md).

A design record does not track the code. Where a document says something is shipped, the code has
moved on since; where it describes a plan, some of it may never have been built. Each one is
described below as what it *is*, and any status it carries about itself is repeated here. **When a
design record and the code disagree, the code is right.**

## The Custom Component creator

The creator's redesign plan (`custom-component-creator-redesign-plan.md`) went with the rest of
the design-note tree. Its §1–§11 had all shipped; its §12 roadmap — the array primitive and
indexed repeats landed, the arpeggiator write-side, responsive anchors, theme tokens and the
sharing gallery did not — is in git history only.

This used to be a four-document chain, read in order. The other three are retired, and what
outlived them is here rather than in a document that reads as open:

- **Properties panel review** — the taxonomy diagnosis. It produced the four-stage restructure,
  all four of which shipped on 2026-07-12 and are verifiable in the code: the tabs are gated on
  `componentWorkspaceMode`, `CustomDesignerEditor.svelte` is gone, `CustomInteractEditor` is the
  cluster view, `CustomReactEditor` is the React group with its sub-nav. Its closing "what not to
  do" was guidance, not work, and is now §2 of the redesign plan.
- **Properties panel restructure stages** — the plan those four stages came from. Its one
  remaining half, the W0 decomposition, was done on 2026-08-23.
- **Designer workspace review** — closed out the same day: regressions restored, five bugs fixed
  or verified, Tier 0 and Tier 1 complete, the feasible Tier 2 items done, the theming pass
  applied, and the §5 decomposition finished at eight components. The decisions it raised that
  nobody acted on are in [known-issues.md](../known-issues.md). Pinned by
  `CE/web/test/surfaceDecomposition.test.js`.

Two documents are open rather than retired, and they are a pair — read the space plan first:

| Document | What it is |
|---|---|
| [Making room in the properties panel](property-panel-space-plan.md) | *Nothing built.* The panel is 600px wide, four columns, 65 tabs, and the Text tab renders 3,090px tall — four and a half screens, of which two sections are 56%. The proposal is to relocate wide property groups (effects, typography, image layers) into display-panel tabs and compound in-panel widgets, on the argument that the panel is portrait and the dock is landscape and can show you the result while you edit. Establishes that three versions of this already ship — the colour/gradient target stores, `BorderCornerWidget` collapsing 178 fields into one diagram, and `LayerEffectsSection` serving four owners — so the work is generalising a mechanism rather than inventing one. Names the two things that would bite: the panel's search box would stop finding relocated properties, and the dock write path appears not to honour multi-selection. Drawn in [`property-panel-space-mockups.html`](property-panel-space-mockups.html). |
| [Display panel candidates](display-panel-candidates.md) | *A worklist.* The inventory the space plan implies: every `PropertySection` in the app parsed and measured — 214 titles, 285 instances, 44,887px — then ranked by height per owner. Two results worth knowing before arguing about any single entry: the most-repeated sections (`Appearance` in 19 editors, `Colours` in 5) are already solved, because `SwatchCluster` hands off to the Colors tab from 53 call sites; and 166 of the 214 titles are under 200px per owner and should be left alone. Ten candidates with a measured size, a verdict and a proposed shape, plus what is deliberately not a candidate. |
| [The Effects tab](effects-tab-design.md) | *Built.* Candidate 1 worked through: the largest relocation at 1,902px over four owners, and the design that falls out of two findings. Each text effect carries an `*Order` number and stacking is set by typing eleven of them, but `CanvasControl.svelte` already sorts them into a stack every frame with the fill as a row in it — so the tab can show the renderer's own stack and dragging writes the numbers back, with no data or renderer change. And `Background.Fill.layerOrder` is already a reorderable array, so the app knows the pattern. Four columns: stack, live specimen with a base/hover/pressed/disabled strip, the selected effect's settings, a shelf of named looks. No sliders anywhere — numbers use `NumberCell`, whose label is a drag handle. Drawn in [`effects-tab-mockups.html`](effects-tab-mockups.html). |
| [The Typography tab](typography-tab-design.md) | *Built.* Candidate 2: 1,317px, and two findings. `Text.Position` has 37 fields and `flowMode` has thirteen values, but the panel has exactly one `{#if}` in the whole Flow section — so with Circle picked you are shown wave amplitude, spiral turns and eight bezier numbers, every one inert and drawn like the two that work. And `Font` carries 24 of its 40 properties as the same seven fields three times (underline, strikethrough, overline) while the renderer already reads them by kind. The tab shows a mode's own parameters and nothing else, one decoration editor with a line picker, families set in their own faces, and a weight ramp. The three modes whose value is a shape get draggable points; everything else stays a number. Drawn in [`typography-tab-mockups.html`](typography-tab-mockups.html). |
| [The Assets tab](assets-tab-design.md) | *Built.* Candidate 3: 1,073px, and a defect. `Assets.images` and `Assets.filmstrips` are name-keyed maps picked from two `<select>` dropdowns with one preview at a time, which is no way to choose a picture. The finding worth building for is arithmetic: `InteractivePartRenderer` takes the whole strip image to be exactly `frameCount` frames, so a file carrying anything else — stray rows, or a count that is simply wrong — is sliced at the wrong pitch and the error grows to a whole frame or more by the end of the strip. Nothing in the application checks it, because the check needs the image's natural size and the asset only stores a rounded per-frame one. (The first version of this entry said the positioning itself drifts. It does not; the record says so and the browser checks now measure what does.) The tab is one library grid for both kinds, a stage that tiles the frames as separate boxes using the renderer's own CSS, and a bar that runs `height % frameCount` and offers the nearest plausible counts that do divide. Two smaller findings came out of the same measurement: the package exporter reads a `width`/`height` off a filmstrip that nothing has ever written, and an image's recorded size goes stale silently. No sliders: step buttons, a typed frame number and the strip itself. Drawn in [`assets-tab-mockups.html`](assets-tab-mockups.html). |
| [The Screen tab](screen-tab-design.md) | *Built.* Candidate 4: the two display editors, measured in a browser rather than estimated — 3,814px at a load a real panel reaches, and all of the growth in the three sections that hold a list. Three findings. `composeLayout` DROPS a zone whose row is past the last row and CLAMPS one whose columns run past the last column, and a clamped zone still paints, one cell wide at the edge, which reads as a rendering bug; nothing checks it and the trigger is the Rows and Cols fields at the top of the same panel. Page rules are first-match-wins, the editor's own tooltip says to put specific ones first, and there is no way to move one. And the same idea got direct manipulation on one component and a nine-column table on the other: `PixelDisplayRenderer` drags and resizes its elements already, `LcdDisplayRenderer` has no drag code at all. The tab is one screen at a workable size with the regions drawn on it, pages as thumbnails composed by the renderer's own composer, and rules you can finally reorder, with the live one marked and unreachable ones flagged. Drawn in [`screen-tab-mockups.html`](screen-tab-mockups.html). |
| [The API tab](api-tab-design.md) | *Built.* Candidate 5, and the measurement inverts the usual argument: the sections that DEFINE what a custom component publishes render at exactly the same height for fifty entries as for eight — 198px, 198px, 256px — because they show one entry at a time behind a dropdown, three times over, while the surface that merely consumes the contract lists it all and grows to 2,203px. The list already exists twelve pixels away, read-only, in the API Preview. Two findings beyond that, both measured against the shipped code before being written down. "Will a consumer see this entry?" has three answers in the application and they disagree: for a path resolving on its first segment and nowhere after, package validation says nothing, the author's editor says nothing, and the instance panel silently drops the row. And the application's own factory publishes `accentColour` against a `variable` rather than a `channel`, which nothing reads — so every custom component made from it ships with an input no consumer can see. The tab is one sortable table over all three maps, with the consumer's answer on the row and package warnings attached to the rows they name. Drawn in [`api-tab-mockups.html`](api-tab-mockups.html). |
| [The Library tab](library-tab-design.md) | *Built — but not for the space.* Candidate 6 was ranked medium and doubted itself: "a dock tab is for things you keep open while working". Measured, the doubt was half right — `CustomPackageLibrary` is 459px empty, 647px with three packages and 647px with twelve, because its grid is capped at 282px and scrolls, so the space argument fails outright and is recorded as failing. What survives is that neither existing surface is a component palette: the library shows a picture of each package and its only use action OVERWRITES the component you have selected — it never calls `addCustomComponentPackage` — while the Insert panel can place one and shows `entries.slice(0, 6)` with no picture at all. And the picture is a second renderer that loses both ends of the layer stack: measured on a 22-part component, the envelope keeps parts 4-21 and the card draws 4-17. The tab is a palette of every saved component drawn by the real renderer, searchable and sortable, placed by click or drag. Drawn in [`library-tab-mockups.html`](library-tab-mockups.html). |
| [The Animation tab](animation-tab-design.md) | *Built — but not for the space.* Candidate 8, and the space argument was measured and rejected first: `AnimationsEditor` is 121px empty and **712px** with one animation, three animations or eight, because it shows one at a time behind a dropdown. The two other sections the candidate list counted are a different feature — Animation in `Display` and `PixelDisplay` plays a GIF or sprite sheet behind a dot-matrix screen — so they stay where they are. What survives is four findings. Two of the seven properties the editor's dropdown offers, Fill Colour and Text Colour, animate nothing at all: the runtime fills transform, opacity or size buckets and has no colour bucket, measured by running the real runtime over each of the seven. What an animation changes is a twelve-row JSON textarea you must hand-edit to delete or reorder. Easing is four names with no picture, though the runtime knows five (`inQuad` is never offered) and the app draws curves elsewhere. And `kind` is a free text box — the mildest of the four, and softened after reading the source, because the cell's own hint already says transition is the only kind that works. The tab lists every animation at once, marks each dead target amber with which kind of nothing it is, warns before you add one, and draws all five easings. Drawn in [`animation-tab-mockups.html`](animation-tab-mockups.html). |
| [The Designer tab](designer-tab-design.md) | *Built, three designers of fourteen.* Candidate 9, which the list called the most interesting and the largest. Fourteen components have content that is a drawing — a pattern, a curve, a register, a keyboard split — and none of it can be authored. The properties panel has no drawing surface for any of them: an envelope curve is one row of two number boxes per node. Preview mode does have drawing, and preview is a REHEARSAL — `previewRehearsal.js` photographs the panels store on start and restores it on stop, deliberately, so a runtime script cannot edit the author's file; a hand-drawn pattern goes back with it. Probed against the real stores: draw two cells into a Phrase during preview, leave preview, the pattern is the eight starter cells again. The Step Sequencer is worse off than the other thirteen — it cannot be drawn even in preview. `stepSequencerLayout.js` exports 24 things, seven are never imported anywhere, and five of those seven are the editing half: `cellAtPoint`, `cellAt`, `isCellOn`, `toggleCell`, `setCellVelocity`. Its default pattern is `{}`, so it draws an empty grid and plays silence in the editor, in preview and in the exported player. The renderer meanwhile draws each cell's opacity from a velocity nothing could set. The tab is a registry — one tab, many editors — each drawing with the component's OWN renderer and writing through its own layout module; three are built (Step Sequencer, Envelope, Turing) and the eleven that are not are named on screen. Measured at 8,143px over fourteen editors, the largest figure in the list, and the tab recovers none of it, because what it adds is the part the panel does not have. Drawn in [`designer-tab-mockups.html`](designer-tab-mockups.html). |
| [Getting from the properties panel to a dock tab](panel-to-dock-handoff.md) | *Built, step 1 of four.* Eight dock tabs existed and not one could be reached from the properties panel: a grep for `displayTabRequest` found four setters in the whole application — the colour swatch, the canvas Align menu, one gradient button, and the custom design surface's own local dock — and none of the eight. The way in is an icon in the section header, in the `tools` slot `PropertySection` already provides, carrying the same icon as the tab it opens; sixteen of them across twelve section editors. Colours is the precedent and cannot be copied exactly, because a swatch IS the value and none of these eight has a widget like that. Both halves are needed — arming a target without requesting the tab lands the user on whatever tab they left open. Building it uncovered a real bug in all seven arming tabs: each opened with "if nothing of MY kind is armed, arm the selection", so the still-mounted Animation tab took the dock back the moment the Sequence opener armed a designer target. `armEditorTargetIfIdle` is the fix and a test reads all seven tabs to keep it. Also records a `stopPropagation` that was never needed and a resize feedback loop in the Designer stages. |
| [Keeping the properties panel's search working](panel-search-index.md) | *Built, step 2 of four.* The panel's search has no index: `PropertySection` and `PropertyCell` read one filter string and hide themselves when it does not match, so search finds a property only while the panel is drawing its row. Move the Effects rows into a tab and typing "glow" returns nothing — not "it moved", nothing. The eight `all…FieldLabels()` functions each tab shipped "ready for that day" were called zero times; `dockFieldIndex.js` calls them, 195 labels, and offers the tab that owns a match with a button that opens it, scoped to tabs that apply to the selected control. **And the search was broken anyway.** A PARTIAL match killed the panel with `effect_update_depth_exceeded` — measured on a bare BehaviorEditor with nothing else on the page: "x", "gl", "t", "to" all looped, "glow" (matching none of its rows) did not — so it fired on every keystroke of a real search, and the page never recovered. The cycle was child-writes-parent-state: each PropertyCell reported its visibility into the section's `$state` counter, which re-ran the section, which re-ran the cells. The count is now a plain number and only the boolean the template needs is mirrored into state, in a microtask. |
| [Image and texture layers: not a tab](fill-layers-not-a-tab.md) | *Rejected, nothing built.* Candidate 7 worked through and turned down. `LayerEffectsSection` is already a shared, parameterised editor over sixteen properties serving all four of its call sites, measured at 510px per expanded layer, and it draws every property the renderer reads. Text's narrower image and texture sections are narrower correctly: `buildTextFillLayerStyle` reads only tint, opacity, fit and offsets, so handing Text the shared editor would draw eleven dead controls. Also records a finding that was nearly published and was wrong — a `PropertyCell label=` grep made saturation, brightness, contrast and greyscale look like rendered properties with no editor; they are drawn as scrub controls in a cell with no label of its own, and the test written to pin the claim failed immediately. |
| [A widget model for the creator](widget-model-creator-plan.md) | *Nothing built. Reordered behind the space plan.* Why a starter leaves eleven anonymous nodes: the creator offers a graph of nine primitive lists joined by name strings, or a one-shot patch that dissolves into it, with no persistent object between. Proposes a `Widget` node that stores the grouping instead of inferring it, compiles down to the primitives the runtime already renders, and unpacks one way. Two things were withdrawn after review: the eight-control cap (the space plan supersedes it — the count is not the problem) and the arc, endpoint and inflate canvas handles (too fiddly; only the count handle survives). Drawn in [`widget-model-mockups.html`](widget-model-mockups.html). |

## Post-beta bets

Plans, not commitments. Each says what the thing is, why it would matter, and what it would cost —
written to be argued with before anybody builds one. The overview is
[beta differentiation](../beta-differentiation.md).

| Document | What it is |
|---|---|
| [The rack canvas](rack-canvas-plan.md) | *Nothing built.* Why the instrument host reads as a form rather than an instrument, and the proposal it deserves: thumbnail nodes on a canvas, wired the way Reason cables devices, with one bottom dock showing whichever node is selected. Names the tension that decides it — Reason's wires imply arbitrary routing and this engine's topology is deliberately constrained — and carries a running idea log. |
| [Tier 3 moonshots](tier-3-moonshots.md) | The post-beta bets, ranked, and the Tier 1 story in plain English. |
| [The Sound Browser](sound-browser-plan.md) | *Stages A–F built, B2 included.* The preset system, which is what the product this succeeds was bought for. The proposal is to index sounds rather than files — one record for a vendor preset, a captured state, a hardware patch, a chain or a rack — and to play every one of them once, offline, so the browser filters on what was measured rather than on what a vendor typed. Instant audition from the probe render, versions instead of overwrites, a map, and a substitute when the plug-in is missing. Five screens are drawn in [`sound-browser-mockups.html`](sound-browser-mockups.html). Stage A — the workspace, facets with exclusion, counts that predict the click, saved queries — is in `SoundBrowser.svelte` over `LibraryQuery` in `Library.h`. Stage B is the auditioner: `SonicProbe.h` plays every preset once and `SonicProfile` is what it wrote down, which is what the measured range filters, the drawn thumbprints and the duplicate fold all read. Stage C is instant audition: the render is kept as a small FLAC so a click makes a sound now while the plug-in loads behind it, and `RecentPlay` remembers your last few bars so the handoff plays your own line rather than a middle C. Stage D replaces overwriting with versions — a retention rule rather than a rail is the design work — and compares two saves by parameter through the plug-in that understands them. Stage E spends the distance function three times — "sounds like", a map of two measured axes whose rectangular selection IS a saveable query, and the nearest thing you own when a rack's plug-in has gone. Stage F puts the library on the hardware without naming a device: a surface arrives as its capabilities and the browser is built to fit it, or is told in a sentence what it cannot do — and the bytes now travel, on the knob page the device already has, over the command surface the workspace uses, so the screen follows the hands. Stage B2 moves the listening into a child process — the worker reports a line per preset, so a crash at preset 300 keeps the 299 before it and blames the one sound that caused it rather than the whole plug-in. Each stage ends with what building it found. Ends with what a real VST3 found that the stub could not — a bug in which every preset was measured with the previous preset's sound. |
| [Capture Session](capture-session-plan.md) | Learning a synth from the synth: turn its knobs, watch what it sends, write the profile. |
| [Total Recall](total-recall-plan.md) | Hardware that behaves like a plugin — the session restores the rig's state. |
| [Ctrlr import](ctrlr-import-plan.md) | Reading the existing Ctrlr panel library, so a user's collection is not stranded. |
