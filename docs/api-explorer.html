Panel scripting

Add your own behaviour to a panel

A panel can hold scripts. A script lets the panel do things the controls alone cannot do. It can send a special message when a button is pressed. It can work out one value from another. It can fill the whole panel from data the synth sends. You can write scripts in Lua, JavaScript, TypeScript, Python or a C‑like language. All of them use the same set of commands. A script works the same way while you build the panel and in the finished plugin. If it works while you test it, it works when you share it.

01 · What a script is

You write what should happen. The panel decides when it runs.

A script is a list of things to do when something happens. You do not start the script yourself. You do not stop it either. Instead, you write a section with a special name. The panel runs that section when the matching event happens. For example, attach a script to a knob. Give it a section called onValueChanged. That section runs every time someone finishes turning the knob.

Every action in a script is a command. You call a command by its name. A small set of core commands is always available. set, get and log are the ones you will use most. All other commands live in groups called modules. You switch modules on for the panel. The Modules lesson explains this. You can write a module command in two ways. ce.midi.sendCC shows which module it comes from. Plain sendCC is shorter. Both do exactly the same thing. Use the one you like better.

You do not need to set anything up first. There are no files to include. There is no step to run before your script works. Tick the modules the panel needs. Then every command in them is ready when your first line runs.

A knob that sends a CC

function onValueChanged(value)
  sendCC(1, 74, value)
  log("cutoff", value)
end
function onValueChanged(value) {
  sendCC(1, 74, value);
  log("cutoff", value);
}

02 · Addressing

You reach a control by the name you gave it

To read or change a control, use its name. Not a hidden number. Use the name you typed in the editor. If you named a knob "cutoff", write "cutoff" in your script. Add a dot to reach a detail of the control: its value, its colour, or any other setting.

The name on its own means the control's value. So get("cutoff") and get("cutoff.value") give the same answer. If you rename the control later, every script that uses the name is updated too. Nothing breaks.

You can read a value in three ways. .value is the real value you would read on the front panel, like 8000 Hz. .normalizedValue is the same value as a position between 0 and 1. This is useful when two controls with different ranges must move together. .midiValue is the number that is sent to the synth.

set tells you if it worked. If you mistype a name, there is no control to change. Then set does nothing and reports failure. Check the answer when it matters. Otherwise a typo does nothing, and you will not notice.

Reading and writing

local hz = get("cutoff")
local pos = get("cutoff", "normalizedValue")

set("cutoff.value", 8000)
set("cutoff.normalizedValue", 0.5)
set("led.background.fill.colour", "#39D98A")

if not set("cutof.value", 1) then
  logError("no control called that")
end
const hz = get("cutoff");
const pos = get("cutoff", "normalizedValue");

set("cutoff.value", 8000);
set("cutoff.normalizedValue", 0.5);
set("led.background.fill.colour", "#39D98A");

if (!set("cutof.value", 1)) {
  logError("no control called that");
}

03 · Writing and the synth

When your script changes a control, the synth is normally told too

When your script changes a control, the panel treats it like a change by hand. The control updates on screen, and the synth is told. This is almost always what you want.

There is one exception. Sometimes your script reacts to a message the synth just sent. If your change went straight back, the panel and the synth would answer each other without end. So a change made while you handle an incoming message is not sent back automatically. You do not need to remember this or set anything. The panel keeps track of why the change happened.

You can change this rule for a group of lines. Two examples. A button resets forty controls to a starting patch. It should update them all first, and tell the synth only after that. A reply that confirms a setting must go out, even during an incoming message. Wrap the lines in noTransmit or transmit. Normal behaviour returns when the group ends. This is true even if an error happens inside the group.

One setting for a whole block

noTransmit(function()
  set("cutoff.value", 8000)
  set("reso.value", 40)
end)

transmit(function()
  sendCC(1, 74, 64)
end)
noTransmit(() => {
  set("cutoff.value", 8000);
  set("reso.value", 40);
});

transmit(() => {
  sendCC(1, 74, 64);
});

04 · Preview puts things back

A preview is a rehearsal, not an edit

Turn the preview off and your panel is exactly as you left it. Everything the preview changed is put back: a knob you dragged, a colour a script set, a control a script made. This is on purpose. A script can run a hundred times while you work on it, and it never slowly rewrites the panel underneath you.

Sometimes you mean it. You write a script that recolours forty controls, you run it once, and you want to keep the result. Say so with ce.panel.keep. Give it a path to keep one property, or call it with nothing to keep everything that run did. It answers true if something was kept.

Two things are never put back, because they cannot be. MIDI you already sent is gone out the wire. Anything you stored with ce.storage.saveSetting was stored because you asked for it to last. Controls a script created are the other way round: they are always cleared, even by keep, because the next run builds them again and a kept one would sit next to its own copy forever.

None of this applies to the exported plugin. There is no preview there — the plugin owns its panel, and nothing is put back. ce.panel.keep is marked panel view only for that reason: in the plugin it has nothing to do.

Keeping one change, and keeping the lot

set("Cutoff.Background.Fill.colour", "#5B9BD5")
ce.panel.keep("Cutoff.Background.Fill.colour")

for _, name in ipairs({ "Cutoff", "Reso", "Drive" }) do
  set(name .. ".Background.Fill.colour", "#5B9BD5")
end
ce.panel.keep()
set("Cutoff.Background.Fill.colour", "#5B9BD5");
ce.panel.keep("Cutoff.Background.Fill.colour");

for (const name of ["Cutoff", "Reso", "Drive"]) {
  set(name + ".Background.Fill.colour", "#5B9BD5");
}
ce.panel.keep();

05 · Reacting

Three ways to hear that something happened

Some events happen to the control your script is attached to. For those, write a section with the matching name. onValueChanged runs when the value settles. onClick runs when the control is clicked. onNoteIn runs when a note arrives. There is nothing else to set up. The name alone makes the link.

You can also listen to something else: another control, the transport, or one of the components. Use on and name what you are listening to: on("cutoff", "onValueChanged", …). Listen to "*" to hear about all of them. The data your section receives always says which control the event came from.

Two event names look almost the same. The difference matters. onValueChange runs again and again while a knob is being turned. Use it for things on screen that should follow the knob. onValueChanged has a d at the end. It runs once, when the knob is released. That is the moment to tell the synth.

watch is the third way. It is not tied to any event. You give it something to watch, and it runs whenever that thing changes. Use it for settings that no event covers, like a colour or a size.

With on, both spellings of an event name work. "step" and "onStep" mean the same thing. You do not have to remember which one this page used.

Three ways to hear about it

function onValueChanged(value)
  sendCC(1, 74, value)
end

on("*", "onStep", function(step)
  set(step.target .. ".led", true)
end)

watch("cutoff.background.fill.colour", function(c)
  log("colour is now", c)
end)
function onValueChanged(value) {
  sendCC(1, 74, value);
}

on("*", "onStep", (step) => {
  set(step.target + ".led", true);
});

watch("cutoff.background.fill.colour", (c) => {
  log("colour is now", c);
});

06 · Modules

Switch on the command groups your panel needs

There are 761 commands in total. They are sorted into 41 groups called modules. A panel that carried every command would be too large. So you tick only the modules your panel uses. Only those are included when you share the panel. The section What it weighs shows the real sizes.

ce.core is always on. Its commands never need a prefix. That is why you write plain set and get. Commands in the other modules can be written in both ways. ce.midi.sendCC and sendCC are the same command.

You may call a command from a module you have not switched on. Then nothing happens. The console tells you which module to tick. Your script keeps running.

A script can ask what it has. ce.has("ce.midi") answers whether that module is both switched on and reachable from where the script is running right now, so a panel-view module answers false with the window closed. ce.modules is the whole list, ce.runtime says which of the two places you are in, and ce.language names the language the script is written in. Use them to write one script that adapts, instead of two that nearly match.

Your scripts can run in two places. The first place is the panel window, while it is open. The second place is the plugin itself, with the window closed. In a DAW, people close the plugin window all the time, and the plugin keeps making sound. Your scripts keep running there too. Timers keep ticking. MIDI keeps arriving. Some commands need the window. Drawing, asking the user a question, and driving the components are like this. With the window shut, there is nothing to draw on and no one to ask. The reference marks these commands panel view only. Calling one with the window closed does nothing, and a note goes to the log. All other commands are marked cross-runtime. They work the same in both places.

Two spellings, one function

-- ce.core is global
set("cutoff.value", 8000)

-- everything else, either way
ce.midi.sendCC(1, 74, 64)
sendCC(1, 74, 64)

local n = ce.music.quantize(63, 60, "minor")
local m = quantizeNote(63, 60, "minor")
// ce.core is global
set("cutoff.value", 8000);

// everything else, either way
ce.midi.sendCC(1, 74, 64);
sendCC(1, 74, 64);

const n = ce.music.quantize(63, 60, "minor");
const m = quantizeNote(63, 60, "minor");

07 · Musical time

Work in beats and bars instead of milliseconds

ce.time knows the current tempo. While you build, the tempo comes from the editor. In the finished plugin, it comes from your music software. ce.time converts between beats and milliseconds for you. For example, you can set a delay time to a dotted eighth note in one line. Almost every synth panel needs that calculation at some point.

There are three ways to make something happen later. after runs it once, after a number of milliseconds. startTimer repeats it at a fixed rate. syncTimer repeats it on a musical interval, such as every sixteenth note. It speeds up or slows down with the tempo.

onBeat and onBar are checked about thirty times per second. So they run very close to the beat, but not exactly on it. That is close enough to light an indicator or to advance a sequencer. It is not exact to the sample. Do not use it for anything that must line up perfectly with recorded audio.

Wait, then send

sendProgramChange(1, 12)
ce.time.after(40, function()
  sendDump("patch")
end)

local ms = ce.time.beatsToMs(0.75)
set("delayTime.value", ms)

ce.time.syncTimer("step", 0.25)
function onTimer(info)
  if info.id == "step" then step() end
end
sendProgramChange(1, 12);
ce.time.after(40, () => {
  sendDump("patch");
});

const ms = ce.time.beatsToMs(0.75);
set("delayTime.value", ms);

ce.time.syncTimer("step", 0.25);
function onTimer(info) {
  if (info.id === "step") step();
}

08 · Components

Set up a component, and hear back from it

The big components each have their own module of commands. These are the arpeggiator, the chord pad, the sequencers, the envelope, and the displays. The Reference shows a picture of each one. Every command starts with the name of the control. Every command tells you if it worked. If you ask for something the component does not have, the command says no. It does not store a setting that does nothing.

read asks a component for its current setting. It uses the same words you would use to set it. Some components hold a list of things: steps, nodes, breakpoints, or destinations. For those lists, size tells you how many items there are. fill replaces all the items at once. insert and remove change one item.

Components also tell you when things happen: a step plays, a scene changes, a pad is hit, a recording finishes. These events need the panel window to be open. That is where the components run.

Ask, set, react

if not ce.components.arp.pattern(a, "chord") then
  logError("that pattern does not exist")
end

local now = ce.components.arp.read(a, "pattern")
local n = ce.components.turing.size(t, "step")
ce.components.turing.fill(t, "step", {0, 0.5, 1, 0.25})

on(a, "onStep", function(step)
  log("step " .. step.index .. " of " .. step.of)
end)
if (!ce.components.arp.pattern(a, "chord")) {
  logError("that pattern does not exist");
}

const now = ce.components.arp.read(a, "pattern");
const n = ce.components.turing.size(t, "step");
ce.components.turing.fill(t, "step", [0, 0.5, 1, 0.25]);

on(a, "onStep", (step) => {
  log(`step ${step.index} of ${step.of}`);
});

09 · Typography

Set text and fonts safely

You can already change any text setting with set. For example, set("Label.Text.Font.size", 18) works. So ce.text does not reach any further than set. It exists for three things you cannot do by writing a setting directly.

It knows which fonts exist. fonts() lists the fonts you can really pick. font("Inter Tight") gives details about one font. It gives nothing if the font is not there. So if you ask for a missing font, you find out at once. The name is not stored while the screen quietly shows another font. Also check the portable field before you choose a font. A built-in font works everywhere. A font from your own library lives only on this computer. It is not part of the panel. It looks right while you build. For the person you send the panel to, it falls back to a different font.

It keeps related settings equal. Boldness is stored in two places. Different parts of the app read different ones. If you change only one, the editor and the finished panel disagree about how bold your text is. style() always writes both. So that problem cannot happen.

It can measure text. measure() tells you how much room a control's text needs in its own font. It uses the same code that draws the text. So spacing and wrapping are included. fit() shrinks the font size until the text fits the control. It also tells you the final size. That is useful when you want to line up something else with the text.

These commands need the panel window to be open. The font list belongs to the editor. Measuring needs a real screen to measure on. A command that guessed the answer would be worse than one that says it cannot help right now.

Check, style, fit

local face = ce.text.font("Inter Tight")
if not face or not face.portable then
  face = ce.text.font("Arial")     -- survives the export
end

ce.text.style("Readout", {
  family = face.family, size = 18,
  bold = true, tabularFigures = true,
})

if face.variable then
  ce.text.axis("Readout", "wght", 620)
end

set("Readout.Text.content", patchName)
local fitted = ce.text.fit("Readout", { min = 9 })
if not fitted.fits then
  logWarn("still overflowing at " .. fitted.size)
end
let face = ce.text.font("Inter Tight");
if (!face || !face.portable) {
  face = ce.text.font("Arial");    // survives the export
}

ce.text.style("Readout", {
  family: face.family, size: 18,
  bold: true, tabularFigures: true,
});

if (face.variable) {
  ce.text.axis("Readout", "wght", 620);
}

set("Readout.Text.content", patchName);
const fitted = ce.text.fit("Readout", { min: 9 });
if (!fitted.fits) {
  logWarn(`still overflowing at ${fitted.size}`);
}

10 · Keeping things

Keep data for a short time or for good

state is your own note pad. Anything you put in it is still there the next time your script runs. It is wiped when the panel is reloaded. Use it for counting things or for remembering where you got to.

Settings are for things that should still be there tomorrow. You choose how far each setting travels. "panel" stores it with the panel. It goes wherever the panel goes, and every script on the panel can see it. "script" stores it for your script alone. "local" stores it on this computer only. It is never part of the panel. For example, a panel you send to someone else should not carry your choice of MIDI port.

encode turns a value into text. decode turns that text back into a value. Use them to fit structured data into a place that only takes text. They are built in for two reasons. Not all five languages have their own version. And all five must produce exactly the same text. Because the text is always the same, you can also compare two values by comparing their text.

Short-term, saved, and local

state.hits = (state.hits or 0) + 1

ce.storage.saveSetting("bank", 3)
ce.storage.saveSetting("port", "IAC",
                       { scope = "local" })

local patch = { name = "Lead", cutoff = 0.75 }
sendSysex(toAscii(ce.storage.encode(patch)))

local back = ce.storage.decode(text)
if back == nil then logError("bad config") end
state.hits = (state.hits ?? 0) + 1;

ce.storage.saveSetting("bank", 3);
ce.storage.saveSetting("port", "IAC",
                       { scope: "local" });

const patch = { name: "Lead", cutoff: 0.75 };
sendSysex(toAscii(ce.storage.encode(patch)));

const back = ce.storage.decode(text);
if (back === undefined) logError("bad config");

11 · When it breaks

Find out what went wrong

Three commands write to the script console. Use log for normal messages. Use logWarn for something odd. Use logError for something that failed. Each level looks different in the console. So a real problem does not look like a note to yourself.

Reporting an error does not stop your script. The rest of the section still runs. If you want to stop, raise an error in your own language's way.

onError is the safety net. Write a section with that name. It is told about every failure your script did not handle. This lets a panel report its own problems when no one is watching the console. Failures are always written to the console as well. So a broken onError section cannot hide them.

Most commands that can fail do not raise an error. They return false instead. set, saveSetting, and every component command work this way. Checking the answer is usually simpler than catching errors.

Three levels, and onError

log("normal")
logWarn("odd, but carrying on")
logError("could not do that")

function onError(info)
  log(info.scriptId .. " failed in " .. info.phase)
end
log("normal");
logWarn("odd, but carrying on");
logError("could not do that");

function onError(info) {
  log(`${info.scriptId} failed in ${info.phase}`);
}

Tutorials

These tutorials are longer than the lessons. Follow each one from start to finish. Every line in the code really runs. The numbers in the comments are the real values the calls returned. The test suite builds each of these panels again on every change, in both languages, and checks the results match. If a tutorial goes stale, the build fails.

01 · A button, from nothing

One button, using the commands from the manual

This tutorial builds a single button. It uses most of the commands from the manual. Every line below really runs. The numbers in the comments are the real values the calls returned. The test suite runs the whole script again on every change.

This is a panel script. The code sits in the onPanelBuild section. That section is for building things. Before it runs, the editor removes everything the script created last time. So running the script twice cannot create two of everything.

Three steps are easy to get wrong. First, create() returns the name it actually used. If the name you asked for was already taken, the returned name is different. Always keep the name it gives you.

Second, a control's fill has layers: a solid colour, a gradient, an image, and an overlay. You control the order of the layers. In the states below, the script changes the gradient's opacity, not the colour under it. A gradient at full opacity hides the solid layer completely. Changing that hidden colour would store a value nobody can see.

Third, watch the spelling. A gradient stop uses color. That is the US spelling, with 6 digits. The fill around it uses colour. That is the British spelling, with 8 digits (AARRGGBB). The gradient editor is older than the rest and kept its own spelling.

bind() says yes even for a parameter that nothing has declared yet. This is on purpose. A script is allowed to declare the parameter later. So you must check for the parameter yourself. The guard in the code below does that check.

One button, by hand

local BAY, NAME, LABEL = "Bay", "Engage", "ENGAGE"

function onPanelBuild()
  -- One batch = one undo step and one re-render, however many writes are inside.
  ce.panel.batch(function()

    -- The shell. Parenting is a separate verb; the button then moves with the group.
    ce.panel.create("Group",  { name = BAY,  x = 24, y = 24, width = 320, height = 140 })
    ce.panel.create("Button", { name = NAME, x = 40, y = 52, width = 120, height = 44 })
    ce.panel.parent(NAME, BAY)

    -- Type. Ask the catalogue first: a family nobody has is REFUSED (style returns
    -- false and says why), and a non-portable face renders here but falls back
    -- after export.
    local face = ce.text.font("Segoe UI") or ce.text.font("Arial")
    ce.text.style(NAME, {
      family = face.family, size = 13, bold = true,
      letterSpacing = 0.6, justification = "centred",
    })
    set(NAME .. ".Text.content", LABEL)

    -- Size the button to its own text, through the same layout that paints it.
    local m = ce.text.measure(NAME)     -- { width = 49.8, height = 15.6, lines = 1 }
    set(NAME .. ".Transform.width", math.max(96, math.ceil(m.width) + 48))

    -- The background.
    local fill = NAME .. ".Background.Fill"
    set(fill .. ".colour", "FF1B2233")         -- `colour`: British, 8 digits AARRGGBB
    set(fill .. ".gradientEnabled", true)
    set(fill .. ".gradient", {
      type = "linear", angle = 90, edge = 0,   -- edge 0 = smooth, 100 = hard bands
      stops = {                                -- `color`: US, 6 digits RRGGBB
        { color = "2B3550", position = 0 },
        { color = "161E33", position = 100 },
      },
    })
    set(fill .. ".layerOrder", { "solid", "gradient", "image", "overlay" })

    -- The icon. The library belongs to the EDITOR, not the panel, so an icon is
    -- never portable — guard it, and let an install without it still build.
    local ico = ce.image.asset("power")
    if ico then
      ce.image.icon(NAME, ico.id, { size = 16, tint = "#E8ECF8" })
    else
      logWarn("no 'power' icon in this install — built without one")
    end

    -- The states. Patch what is actually ON TOP. patch() returns how many keys it
    -- merged, so a silent 0 is a spelling mistake you can see.
    ce.panel.patch(NAME, "Hover",    { ["Background.Fill.gradientOpacity"] = 55 })
    ce.panel.patch(NAME, "Pressed",  { ["Background.Fill.gradientOpacity"] = 20,
                                       ["Transform.scale"] = 0.94 })
    ce.panel.patch(NAME, "Disabled", { ["Transform.opacity"] = 0.4 })

    -- The synth.
    if ce.device.parameter("filter.cutoff") then
      ce.device.bind(NAME, "filter.cutoff")
    else
      logWarn("no filter.cutoff in this profile — the button is decorative")
    end
  end)
end

-- Motion. A spring for the press, because it should settle rather than snap;
-- a tween for the glow, because it has a length you want to name.
on(NAME, "pointerDown", function()
  ce.anim.spring(NAME .. ".Transform.scale", 0.94, { damping = 8, frequency = 14 })
end)

on(NAME, "pointerUp", function()
  ce.anim.spring(NAME .. ".Transform.scale", 1.0, { damping = 8, frequency = 14 })
end)

on(NAME, "valueChanged", function(v)
  ce.anim.to(NAME .. ".Background.Fill.gradientOpacity", v > 0.5 and 100 or 40,
             { duration = 180, curve = "outCubic" })
end)

02 · Eight, from a table

Describe the panel once, and let the script build it

This builds the same eight pads. This time a table with eight rows describes them. The table drives everything. Change the number of columns to 2 and the grid reflows. The group resizes to match. Add a ninth row and you get a ninth pad. The new pad is coloured, labelled, wired up, and playing. You change nothing else.

Each part of the code has one job. The list holds the drum kit data. It stays separate from the panel. The function builds one pad from one row. That is why the eight pads always match. Simple arithmetic places each pad and sizes the group to fit. The shade() function computes the darker end of each gradient. You do not type sixteen colour codes. The label comes from the same row that sets the roll rate. So the label and the rate always agree.

The drum roll is a button setting, not a script timer. A button can already repeat while it is held. It has its own delay and interval settings. A script timer would only be a worse copy of that. The script adds one thing a stored number cannot do. It computes the interval from the host tempo. So the roll follows the music.

The handler that keeps its own row has no equivalent setting at all. The script defines one handler. Each pad gets its own copy, and each copy remembers its own row of the table. So each pad plays its own note and velocity. A control can store one note. It cannot store eight different notes and velocities.

An ordinary pad fires onClick once, when you release it. A repeating pad fires it again and again while you hold it. It does not fire again on release, because it has already fired. The same handler covers both kinds.

-- Darken a 6-digit hex. Plain Lua: this is arithmetic.
local function shade(hex, f)
  local out = ""
  for i = 0, 2 do
    local byte = tonumber(hex:sub(i * 2 + 1, i * 2 + 2), 16)
    out = out .. string.format("%02X", math.floor(byte * f))
  end
  return out
end

03 · Asking the instrument

Let the component do the work, then ask it what it did

Tutorial 02 built a drum kit from eight separate buttons. That worked. This tutorial builds the same kit as a single Drum Pads control. The single control is not just shorter. Three features of a drum grid cannot be built from separate buttons at all.

Choke groups. A closed hi-hat has to silence an open hi-hat. Separate buttons cannot do this, because no button knows the other buttons exist. Strike position. The spot where your finger lands sets how hard the note sounds. A plain button cannot tell where you hit it. Corner zones. Each corner of a pad can do a different action, for example a roll or a flam. This gives you many more moves than sixteen plain triggers.

Only set what differs from the defaults. The kit handles the rest. One call to fill() writes all eight notes in one step. You never set the choke groups. The control works them out from the notes. Look at what the script actually stored. Pad 1 stores nothing, because 36 was already its default note. Storing 36 anyway would pin the pad, and it would stop following the base note later.

Ask the control instead of telling it. read() returns what the control settled on, not what you stored. This lets the script work things out. The loop below gives a roll to every pad in a choke group. It finds the hi-hats without any typed pad positions. It names them in the log from the same answer. It stays correct when the kit, the rows, or the columns change.

The roll settings are computed too. The roll rate is a note value, not a number of milliseconds. So a 1/32 roll stays a 1/32 when the tempo changes. The roll delay lets one pad do two jobs. Tap the pad and it strikes once. Hold the pad and it rolls.

Corner zones are set for the whole grid, not per pad. This is on purpose. Your hand learns each corner action once. If a corner meant different things on different pads, the grid would be much harder to play.

04 · A panel is a graph

Connecting controls to each other

The last three tutorials built controls. This one connects them. A meter can follow a knob. An LCD can take its reading from one control and its backlight from another. An arpeggiator can take its notes from a chord pad. With connections like these, the panel is more than a list of controls. It is a set of connections.

You name the control, the same as everywhere else. Inside the editor, the connection is stored in a way that survives a rename. Your script never sees that stored form and never needs to. read() gives you the name back.

Not every control can drive every field. The command tells you when a connection is refused, and that answer is useful. Watch Title in the code below. It is an ordinary label. The LCD accepts it as a backlight source. The meter refuses it as a level source. The two fields need different things. Any control can answer "is this on". Only some controls can answer "how far up is this". The command gives the reason in words: refused — it is not a knob, slider or other range control. A connection that failed silently would look like a working one, until you noticed the meter never moved.

So read the answer each call returns. The loop below tries a list of planned connections. It counts how many connections succeeded. A script that builds on someone else's layout can then handle missing controls instead of half-working.

The last block reads the connections back. It walks the panel, asks what type each control is, and asks each control what drives it. That block uses nothing from the earlier blocks. It would report connections made by hand in the editor just as well.

Naming no control disconnects the field. That is a real setting, not just a missing one. A connection whose target was later deleted also reads back as disconnected. In both cases the control runs on its own value.

05 · A step sequencer

Make the panel play notes, in time, on its own

This tutorial builds a small instrument: eight step buttons, a PLAY button, and a NEW button. Press PLAY and the panel plays a note pattern, in time with the clock. Press NEW and you get a fresh pattern. You need no hardware for this. Everything runs in the preview.

The first block builds the row. Each step is a toggle button. A toggle button holds a value: 1 when it is on, 0 when it is off. That value is the pattern memory. A step plays when its button is on. There is no separate list to keep in sync.

The second block makes a pattern. ce.music.scale(48, "pentatonicMin") gives the five notes of a C minor pentatonic scale. Notes from one scale always sound good together. That is why generated patterns here are never sour. ce.math.euclid(8, 5) spreads 5 hits as evenly as possible over 8 steps. This gives a musical rhythm instead of a random one.

Notice ce.math.seed(state.seed). The random commands in this API are seeded. The same seed number always gives the same "random" pattern, in every language. So a pattern is saved as one small number. NEW just counts the seed up by one. Press NEW three times, and pattern number 3 is always the same pattern number 3.

The third block is the clock. ce.time.syncTimer("beat", 0.25) fires the timer every quarter of a beat. That is a sixteenth note. The timer follows the tempo: turn the tempo up and the pattern speeds up with it. On each tick, onTimer moves one step forward, wraps back to step 1 after step 8, and plays the step's note if its button is on. The last number in sendNote releases the note after 120 milliseconds. You never send a note-off yourself.

Every command in this tutorial is cross-runtime. So the sequencer keeps playing in a DAW with the plugin window closed. That is the second place scripts run, described in lesson 06. One more idea to try: the pattern lives in state, so it is gone when the panel reloads. Save state.seed with ce.storage.saveSetting and restore it in onPanelReady, and your pattern survives.

06 · A synth that does not exist

Teach the app a synth it has never met

Normally a device profile tells the app what your synth understands. This tutorial shows what to do when there is no profile: you teach the app from a script. To keep it followable for everyone, we invent a synth. Call it the FS-1. Its MIDI maker number is 7D. That number is reserved for experiments, so no real synth will ever be confused by it. Because the synth is invented, we will also play its part ourselves. The panel cannot tell the difference. Yours at home will work exactly the same way.

The first block teaches the app two parameters. defineParameter needs one thing above all: how the value reaches the synth. For cutoff that is a plain CC number. That is the simplest form. For resonance it is a SysEx message, written as a template. $value marks where the value goes. $checksum marks where the checksum goes, and $checksumStart marks where the checksum starts counting. The F0 and F7 frame bytes are added for you. A parameter with no way to reach the synth is refused, and the message says why.

The second block builds two knobs and connects them with ce.device.bind. Tutorial 01 warned that bind() says yes even for a parameter nobody has declared. Here is the other half of that story: now the parameters really exist, so the binding really works. Turn the Cutoff knob and CC 74 goes out. Turn Reso and the SysEx message goes out, checksum and all.

The third block teaches the app the FS-1's patch dump. defineDump describes three things. The bytes that ask for the dump. How to recognise the reply: it starts with F0 7D 01 20 and ends with F7. And where each value sits: the payload starts 4 bytes in, cutoff is payload byte 0, resonance is payload byte 1. Every field must name a parameter you already defined. An unknown name is refused at once.

Then we play the synth's part. ce.midi.feed injects bytes as if the hardware had sent them. The reply carries the values 96 and 40. Press RECEIVE and watch: the app recognises the dump, both knobs move to the values from the message, and onDumpReceived fires. With a real synth you would send ce.device.requestDump("patch") and the real reply would arrive the same way.

One rule is doing quiet work here. Values that arrive from the synth are not sent back out to it. The knobs move, and nothing echoes. Without that rule, every dump would answer the synth with a storm of messages carrying the values it just told you.

What your panel carries

What changed

The number of commands roughly tripled across these releases. Six of the releases added nothing new. They fixed things that were quietly doing the wrong thing.

  1. ImagesPictures on a control

    Eight commands for the pictures a control can carry: a background image, an overlay, a picture or texture inside the text, and the icon it shows. There is also a command that lists what is in the icon library.

    Three things here are easy to get wrong. The commands handle them for you. First, background picture layers stack on top of each other. A picture inside text replaces the old one instead. Mix these up and you can build a layer that is set up correctly but never shows. Second, the word fill means two different things. On a background it means crop to fit. On text it means stretch to fit. Third, an icon from your library is stored on your computer, not in the panel. So the icon does not travel with the panel. The embed command copies the icon into the panel so it does.

  2. DrawingDrawing on a control

    Eleven more drawing commands: grids, sets of lines and points, smooth curves, polygons, images, clipping, blending, and a way to group drawing steps together.

    The bigger change is speed. Drawing many small things used to get much slower the more you drew. Drawing 256 line segments took longer than one screen frame allows. Grids, lines, and points are now one command for the whole set. The batch command groups many drawing steps into one screen update. For those 256 segments, this is about fourteen times faster.

  3. ChecksumsChecksums that agree with each other

    Many synths expect a checksum at the end of a message. There are several ways to work one out. Scripts knew three ways. Device profiles knew a different two, under different names. So a script could make a checksum that no profile could describe. And a synth with an unusual checksum could not have a working profile at all.

    Scripts and profiles now read the same list of eleven checksum types. They cannot disagree. If you ask for a type that is not on the list, you get nothing back, plus a message listing the valid types. You do not get a checksum for the wrong synth. This work also found a worse bug. While you built a profile, the editor and the finished export worked checksums out differently. The preview was wrong and the export was right.

  4. This pageThis page

    Every command now has a worked example. Options are shown in a table instead of described in passing. Each description now sits under the command name, not in a wide column you had to scroll sideways to read.

    The example results are generated by running the commands, not typed by hand. Doing this exposed two misleading descriptions. blend looked like it took two numbers. It takes two lists. Passing numbers returned an empty list, which was correct but very confusing.

  5. TextText and fonts

    Seven commands for text: list the fonts, ask what a font can do, set a control's text style, measure text, and shrink text to fit.

    None of this was newly possible. Every text setting could already be changed directly. Three things were missing. Knowing which fonts are really available. Keeping the two places where boldness is stored in agreement, because the editor and the export could disagree. And measuring a control's own text in its own font.

  6. ComponentsComponents report what they are doing

    Components now report eleven kinds of events: a step playing, a cycle finishing, a pad hit or released, a scene or stage changing, a value settling, a bounce, a recall, a zone, a voicing.

    Before this, a script could change every setting of a component but was never told anything back.

  7. ComponentsEvery component setting reachable

    The component commands went from 229 to 302. Every component gained read, so you can ask what it is set to. Components that hold lists gained commands to count, replace, add, and remove items. And every command now tells you whether it worked.

    A real bug turned up here. Many settings offer a fixed choice of values, and most of them listed the wrong values. The arpeggiator accepted a pattern it has never had. It refused "chord", which it does have. The choices now come from the same list each component itself reads.

  8. StorageSaved settings that do not collide

    Saved settings gained the three scopes described in the manual. Two scripts can now save something under the same name without silently overwriting each other. There is also a way to store structured values as text.

  9. PanelArranging controls from a script

    The canvas right-click menu has twenty-seven ways to align and spread out controls. Before, only the menu could use them. Now the menu and your script call exactly the same commands.

  10. DrawingGradients, dashes and colour

    Drawing gained gradients, dashed lines, transparency, and transforms, as well as flat shapes. It also gained the panel's own LCD font and a way to measure text. Eight colour commands were taken from the app's own colour code. So a colour your script lightens matches the border next to it.

  11. DialogsScripts can ask questions

    A script could only show a message. Now it can also ask a question: a choice between buttons, a line of text, or a pick from a list.

  12. AnimationMovement that matches the panel

    Seven more ways to move a value over time. The curves now come from the same shapes the Properties panel stores. Before, they came from formulas that only looked similar.

  13. TimeThe transport's own grid

    Note divisions, bar and beat positions, swing, loops, and tempo worked out from taps or from an incoming clock. Before this, Lua had no clock of its own at all.

  14. MusicScales, chords and voicing

    Scales, chords, voice leading, and arpeggio ordering. The Chord Pad and Harmoniser already did this musical work inside the app. Scripts could not reach it before.

    Reading a flat note name used to fail and quietly return note 0. Note 0 is a real note, so the mistake was easy to miss.
