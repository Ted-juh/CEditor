Panel scripting

Write a script once. It runs in five places.

A CEditor panel can carry scripts in Lua, JavaScript, TypeScript, Python or C‑family source. They call one API. The editor runs it in a WebView while you design; the exported plugin runs the same script in an embedded engine with the window shut. The rule the whole contract is built around is that those must not differ — if it behaves one way while you are testing it, it behaves that way in the export.

Part one · the manual

Ten things, in the order you need them

01 · What a script is

A file of named functions

You do not call into CEditor and wait. You define functions with particular names, and the panel calls them when something happens. A script attached to a knob and named for onValueChanged runs every time that knob settles.

Everything in the API is a plain global function. set, get and log are always there. Everything else lives in a module you switch on — see Modules — and each module member has two spellings: a readable namespaced one (ce.midi.sendCC) and a flat global (sendCC). They are the same function.

There is no import, no require, no build step. A panel declares its modules and the runtime injects them before your first line runs.

A knob that sends a CC

function onValueChanged(value)
  sendCC(1, 74, value)
  log("cutoff", value)
end
function onValueChanged(value) {
  sendCC(1, 74, value);
  log("cutoff", value);
}

02 · Addressing

Everything has a dot‑path, rooted on a name

A control is addressed by the name you gave it, not by an id you never see. From there the path walks into whatever you want: its value, its colour, a section property.

A bare control name means its value, so get("cutoff") and get("cutoff.value") are the same question. Rename a control in the editor and every script that mentions it is updated with it.

A value has three faces. .value is the real one, .normalizedValue is its 0–1 position, and .midiValue is what goes on the wire. Suffix the path, or pass the form as a second argument.

set returns whether it wrote. A path that resolves to nothing is a typo, and it used to fail in complete silence.

Reading and writing

local hz = get("cutoff")
local pos = get("cutoff", "normalizedValue")

set("cutoff.value", 8000)
set("cutoff.normalizedValue", 0.5)
set("led.background.fill.colour", "#39D98A")

if not set("cutof.value", 1) then
  logError("no control called that")
end
const hz = get("cutoff");
const pos = get("cutoff", "normalizedValue");

set("cutoff.value", 8000);
set("cutoff.normalizedValue", 0.5);
set("led.background.fill.colour", "#39D98A");

if (!set("cutof.value", 1)) {
  logError("no control called that");
}

03 · Writing and the synth

A write usually transmits. It knows when not to.

Setting a control normally behaves as if somebody moved it: the panel updates and the synth is told. That is what you want almost always.

The exception is when you are reacting to something the synth just sent. Echoing it back is a feedback loop, so a write made inside an inbound handler is silent automatically. You do not set a flag; the runtime tracks where the write came from.

Override it with a block when you need to. An init‑patch button writes forty controls and should send none of them until it is done; a MIDI‑learn confirmation needs to send from inside an inbound handler. Both auto‑reset at the end of the block, so they cannot leak even if something throws.

Scoped, not per‑line

noTransmit(function()
  set("cutoff.value", 8000)
  set("reso.value", 40)
end)

transmit(function()
  sendCC(1, 74, 64)
end)
noTransmit(() => {
  set("cutoff.value", 8000);
  set("reso.value", 40);
});

transmit(() => {
  sendCC(1, 74, 64);
});

04 · Reacting

Name a function, or subscribe to anything

For a control's own events, define the handler by name: onValueChanged, onClick, onNoteIn. For anything else — another control, the transport, a component — use on(target, event, fn). "*" subscribes to every target, which is why every payload carries the one it came from.

There are two flavours of value change and the difference matters: onValueChange fires continuously while a knob is moving (use it for the GUI), onValueChanged fires once when it settles (use it to transmit).

watch is the third way, and it is not an event at all: it re-runs when a path changes, including nested properties no event covers.

Either spelling works in on — the event's id ("step") or its handler name ("onStep"). Only the second used to.

Three ways to be told

function onValueChanged(value)
  sendCC(1, 74, value)
end

on("*", "onStep", function(step)
  set(step.target .. ".led", true)
end)

watch("cutoff.background.fill.colour", function(c)
  log("colour is now", c)
end)
function onValueChanged(value) {
  sendCC(1, 74, value);
}

on("*", "onStep", (step) => {
  set(step.target + ".led", true);
});

watch("cutoff.background.fill.colour", (c) => {
  log("colour is now", c);
});

05 · Modules

You pay for what you switch on

The surface is 536 members across 40 modules. Injecting all of it into every panel would be wasteful, so a panel declares the modules it uses and the export carries only those. The weights in What it weighs are measured from the real preludes, not estimated.

ce.core is always on and never namespaced — set and get have no prefix. Every other module gives you both spellings.

A member from a module you did not declare returns nothing and says so in the console. It does not throw, and it does not silently do nothing.

Nine modules are cross-runtime; the rest are panel view only, which means they need the window open. Drawing, dialogs and the component families are in the second group because with the window shut there is no surface, nobody to ask, and no component engine running.

Two spellings, one function

-- ce.core is global
set("cutoff.value", 8000)

-- everything else, either way
ce.midi.sendCC(1, 74, 64)
sendCC(1, 74, 64)

local n = ce.music.quantize(63, 60, "minor")
local m = quantizeNote(63, 60, "minor")
// ce.core is global
set("cutoff.value", 8000);

// everything else, either way
ce.midi.sendCC(1, 74, 64);
sendCC(1, 74, 64);

const n = ce.music.quantize(63, 60, "minor");
const m = quantizeNote(63, 60, "minor");

06 · Musical time

Beats, not milliseconds

ce.time reads the transport — the editor's clock, or the DAW playhead when the window is shut — and converts between beats and milliseconds at the current tempo. The delay‑time calculation every synth panel needs is one call.

Timers come in three shapes: startTimer repeats, after fires once, and syncTimer repeats on a musical interval and follows the tempo when it changes.

onBeat and onBar are watched on the message thread at about 30 Hz. That lands within a frame of the beat — right for lighting an LED or stepping a sequencer, wrong for anything that has to be sample‑accurate.

Settle, then send

sendProgramChange(1, 12)
ce.time.after(40, function()
  sendDump("patch")
end)

local ms = ce.time.beatsToMs(0.75)
set("delayTime.value", ms)

ce.time.syncTimer("step", 0.25)
function onTimer(info)
  if info.id == "step" then step() end
end
sendProgramChange(1, 12);
ce.time.after(40, () => {
  sendDump("patch");
});

const ms = ce.time.beatsToMs(0.75);
set("delayTime.value", ms);

ce.time.syncTimer("step", 0.25);
function onTimer(info) {
  if (info.id === "step") step();
}

07 · Components

Drive the arpeggiator, and hear back from it

The interactive components — arpeggiator, chord pad, sequencers, matrix, envelope, displays — each get a module of verbs. Every verb takes the control's name first, and every one returns whether the component now holds what you asked for. A value it does not have is refused, not stored.

read asks what a component is set to, in the same words the verbs use. size, fill, insert and remove work on the lists a component carries — steps, nodes, breakpoints, destinations.

And they raise events: a step firing, a scene changing, a pad struck, a take finishing. Those are panel‑view only, because the component engines run in the editor's surface.

Ask, set, react

if not ce.components.arp.pattern(a, "chord") then
  logError("that pattern does not exist")
end

local now = ce.components.arp.read(a, "pattern")
local n = ce.components.turing.size(t, "step")
ce.components.turing.fill(t, "step", {0, 0.5, 1, 0.25})

on(a, "onStep", function(step)
  log("step " .. step.index .. " of " .. step.of)
end)
if (!ce.components.arp.pattern(a, "chord")) {
  logError("that pattern does not exist");
}

const now = ce.components.arp.read(a, "pattern");
const n = ce.components.turing.size(t, "step");
ce.components.turing.fill(t, "step", [0, 0.5, 1, 0.25]);

on(a, "onStep", (step) => {
  log(`step ${step.index} of ${step.of}`);
});

08 · Typography

The fields were never the problem

Text.Font has 41 fields, Text.Multiline eleven and Text.Position around forty — and set() could always write every one of them by path. set("L.Text.Font.size", 18) has worked since the first release. So ce.text adds no reach. It adds the three things a bare path write cannot do.

It knows what exists. fonts() is the catalogue the Properties panel picks from; font(family) is one entry or nothing. A family nobody has is refused rather than stored — where set() would keep the typo and quietly fall back to a platform default. Read portable before you commit to a face: a builtin is named in every runtime, while a font from the library belongs to this editor install and is not part of the panel document, so it looks right while you build and falls back once exported.

It keeps the invariants. weight and weightValue are a pair, and two different consumers read different halves — the renderer takes weightValue first, the Properties panel reads weight for a non‑variable face. Writing one alone makes the editor and the render disagree, in both directions. style() always writes both, and axis("wght", …) drags the pair along with it.

It can measure itself. measure() reports what a control's text occupies in its own font, through the same layout function that paints it — no size or family handed in, and letter spacing, wrapping and maxLines all honoured. fit() then shrinks Font.size until it fits the box and tells you what it chose. fitMode = "shrink" already scales text down when painting, but that is a paint‑time scale: the stored size never changes, so nothing can ask what it settled on. fit() writes a number other layout can use.

Panel view only, and deliberately: the catalogue is the editor's and the measuring wants a canvas. A typography verb answering from a guess would be worse than one that says it is not there.

Check, style, fit

local face = ce.text.font("Inter Tight")
if not face or not face.portable then
  face = ce.text.font("Arial")     -- survives the export
end

ce.text.style("Readout", {
  family = face.family, size = 18,
  bold = true, tabularFigures = true,
})

if face.variable then
  ce.text.axis("Readout", "wght", 620)
end

set("Readout.Text.content", patchName)
local fitted = ce.text.fit("Readout", { min = 9 })
if not fitted.fits then
  logWarn("still overflowing at " .. fitted.size)
end
let face = ce.text.font("Inter Tight");
if (!face || !face.portable) {
  face = ce.text.font("Arial");    // survives the export
}

ce.text.style("Readout", {
  family: face.family, size: 18,
  bold: true, tabularFigures: true,
});

if (face.variable) {
  ce.text.axis("Readout", "wght", 620);
}

set("Readout.Text.content", patchName);
const fitted = ce.text.fit("Readout", { min: 9 });
if (!fitted.fits) {
  logWarn(`still overflowing at ${fitted.size}`);
}

09 · Keeping things

Three lifespans, and you pick

state is a plain table of your own that survives between handler calls and dies when the script reloads. Use it for anything you are counting.

Settings outlive the session, and they have three scopes. "panel" is shared by every script on the panel and travels with the document. "script" is private to yours. "local" never enters the document at all — a panel you send somebody should not carry your MIDI port choice.

encode and decode are JSON, and they are here rather than in your language because one of the five runtimes has none: the Lua engine opens base, math, string and table. All five produce identical text for identical values, keys sorted, so two structures can be compared by comparing their encodings.

Scratch, saved, shipped

state.hits = (state.hits or 0) + 1

ce.storage.saveSetting("bank", 3)
ce.storage.saveSetting("port", "IAC",
                       { scope = "local" })

local patch = { name = "Lead", cutoff = 0.75 }
sendSysex(toAscii(ce.storage.encode(patch)))

local back = ce.storage.decode(text)
if back == nil then logError("bad config") end
state.hits = (state.hits ?? 0) + 1;

ce.storage.saveSetting("bank", 3);
ce.storage.saveSetting("port", "IAC",
                       { scope: "local" });

const patch = { name: "Lead", cutoff: 0.75 };
sendSysex(toAscii(ce.storage.encode(patch)));

const back = ce.storage.decode(text);
if (back === undefined) logError("bad config");

10 · When it breaks

Three levels, and a handler for the rest

log, ce.core.warn and ce.core.error land at different levels in the script console, so a real failure does not read like a debug print. Note the flat spellings are logWarn and logError: a global called error would shadow Lua's builtin and turn the standard way to raise into a print.

Reporting an error does not stop the handler. To actually stop, raise with your own language's error / throw.

onError catches what a script did not: the failure is always logged as well, so a panel whose own error handler is broken does not go quiet.

Verbs that can fail say so in their return value rather than throwing — set, saveSetting, and every component verb. Checking one is usually cheaper than a handler.

Levels and the backstop

log("normal")
logWarn("odd, but carrying on")
logError("could not do that")

function onError(info)
  log(info.scriptId .. " failed in " .. info.phase)
end
log("normal");
logWarn("odd, but carrying on");
logError("could not do that");

function onError(info) {
  log(`${info.scriptId} failed in ${info.phase}`);
}

What changed

The last ten phases, newest first

The surface roughly tripled over these. Three of them were not additions at all — they were the API telling the truth about things it had been quietly getting wrong.

  1. §46ce.text

    Seven verbs for typography: fonts, font, style, axis, read, measure, fit. The unusual thing about this module is that it adds no reach — all ninety‑odd text fields were already writable by path. What was missing was knowing which fonts exist, keeping weight and weightValue consistent, and being able to measure a control's own text in its own font.

    Found on the way: the warning for a mistyped field on a fixed‑shape section had been dead code since it was written. It hung off the wrong branch of an if, testing for a state that branch could never be in — so set("L.Text.Font.sze", 20) stored a key nothing reads and said nothing at all. It fires now, on both the editor and the player path, because whether a key is new on a typed section is a question about the control, not about who writes it.

  2. §45ce.components events

    Eleven events, so a script can hear back: onStep, onCycle, onHit, onRelease, onScene, onStage, onSettled, onBounce, onRecall, onZone, onVoiced. Before this a script could drive 302 component members and never be told anything.

    Found on the way: on(target, event, fn) only ever matched the handler name, while the events list names events by id — so on("*", "timer", fn) registered a listener that could never fire, silently, since the verb existed. Both spellings work now.

  3. §44ce.components

    229 → 302 members. Every family gained read; the ones with lists gained size, fill, and where an element has a template, insert and remove. Every verb now reports whether it applied.

    And a real bug: 24 of the 28 enum verbs offered values no component has and refused values it does. arp.pattern accepted "converge", which the arpeggiator has never had, and refused "chord", which it does. arp.division offered eight of the transport's fourteen note values while ce.time.divisions() — same panel, same script — already answered from all fourteen. The values now come from the table each component's own code reads.

  4. §43ce.storage

    5 → 10 members. Three scopes, so two scripts saving "count" no longer clobber each other in silence, plus JSON — which exists because the Lua engine has none and all five runtimes must produce identical text.

  5. §42ce.panel

    15 → 24. Twenty-seven alignment operations sat on the canvas context menu and were reachable from nothing else; they are pure functions now, and the menu and the script call the same ones.

  6. §41ce.draw & colour

    Gradients, dashes, opacity, transforms, the panel's own LCD font, text measurement — and eight colour verbs in ce.math, ported from the app's own so a script-lightened colour matches the border beside it.

  7. §40ce.ui

    3 → 9. Ask a question rather than only make a statement: a choice, a line of text, a pick from a list — as dialog shapes, not three more modals.

  8. §39ce.anim

    4 → 11. A real cubic-bezier solver in all four runtimes rather than four lookalike formulas: the panel stores CSS control points, and 1-(1-t)² is not cubic-bezier(.25,.46,.45,.94).

  9. §38ce.time

    9 → 22. The transport's own grid — divisions, bar/beat, swing, loop folding, tempo from taps. Lua had no clock at all: it opens base, math, string and table, so there was no os.clock to call.

  10. §37ce.music

    5 → 13. Scales, chords, voice leading, arp order — the maths the Chord Pad and Harmoniser already did internally, which a script could not reach. noteNumber could not read a flat and returned 0 for anything it failed on, which is a real note.
